## What was produced

The owning design is `docs/_design/G1_PERSISTED_INSTRUCTIONS.md`, still **[SPEC-DRAFT]**, **Not Yet Implemented**, and `PACKS_ALLOWED_FOR_0A_0B_ONLY`. Eighteen numbered outcomes preserve the coupled OI-03/OI-04 objective. The design specifies one shared instruction repository, immutable revisions, per-conversation selection, transactional compare-and-swap, a process-safe conversation lease, explicit idle reload, actual terminal/desktop request composition, model-system preservation, editor/CLI contracts, reversible history and exact storage/wire layouts. These are proposed engineering decisions, not implemented capabilities.

The request paths were traced far enough to identify three concrete integration hazards. The terminal's normal entry supplies no ChatID, and resetChat clears its transcript state without changing that ID; the older curated-context draft's empty-ID-to-default shortcut cannot distinguish separate conversations. Desktop and terminal settings are separate owners. The model server prepends its model-specific system text only if the request does not already start with a system message, so adding custom instructions without explicitly preserving that text would suppress it. Source paths, hashes and exact anchor tokens are in G1_SOURCE_ANCHORS.json; anchor resolution is not complete semantic or closure proof.

## Executed evidence

Two existing instruction transport tests passed through the normal Go runner: TestSessionAddsSystemPromptOnlyToRequest and TestChatSystemCommandControlsBuiltInSystemPrompt. A separate run of TestChatPrompt/no_truncate_with_limit_exceeded passed, with the parent and subtest both reconciled. All four named run/subtest records finished with no failures or skips. These are existing-path baselines, not a G1 persistence/restart/UI result. The commands, real child exits and complete output are retained.

Seven small synthetic cloud requests were executed through the existing local Ollama service. The requested deepseek-v4.1-flash:cloud tag served deepseek-v4.1-flash on successful calls. A 25-input-token prompt completed both with requested num_ctx=4096 and num_ctx=8; that request setting was not enforced as a cloud admission boundary in this observation. Two zero-output requests were rejected with provider HTTP 400, max_tokens must be positive. Three one-token requests reported input counts 25, 502 and 502; the repeated longer requests had identical input bytes. One-token probing performs real inference and incurs overhead; it is not a zero-output tokenizer. These small observations do not prove the provider's maximum context, media counting or universal no-truncation behaviour. No user conversation was supplied to the probes.

An independent raw-JSON construction measured the maximal significant PUT envelope at 407970 bytes under the design's text/binding limits, below the 524288-byte raw-body cap. This corrects the earlier draft's too-small 262144-byte raw-body limit. Padding whitespace still counts towards the body cap. This byte bound is not a token-budget estimate.
