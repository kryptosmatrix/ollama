## Verdict: REVISE

The design is directionally sound and the probe is a real, useful experiment, but the contract as written is not yet safe to implement. Several concrete gaps would let a passing run coexist with a broken or drifted generator, and one requirement (G-02) is stated in a way the probe does not actually establish.

### Concrete findings

1. **G-02 "byte-identical JS" is asserted from `ts.transpileModule`, not from the project's real emit path.** The probe uses `ts.transpileModule` with a hand-picked `opts` object (`target: ES2020, module: ESNext, useDefineForClassFields: true, removeComments: true`). That is not the same as the project's `tsconfig.app.json` (`noEmit: true`, `verbatimModuleSyntax: true`, `erasableSyntaxOnly: true`, `moduleResolution: bundler`, `jsx: react-jsx`, `types: []`). `transpileModule` ignores most of those and does not run the same transform pipeline as `ts.createProgram(...).emit()`. The claim "byte-identical JS under the project compiler options" is therefore not demonstrated by the supplied evidence. Fix: compare emitted JS from a real `Program` emit using the parsed `tsconfig.app.json` options (with `noEmit` overridden only for the comparison), or explicitly narrow the claim to "identical under the recorded transpile options" and stop calling it the project compiler options.

2. **The transform's correctness is asserted by shape-matching, not by a stated invariant.** `type-probe-r2.mjs` throws on unrecognised top-level statements, unknown constructor writes, and unsupported transform expressions — good — but it does not state what it guarantees about the *set* of edits. In particular:
   - It rewrites every `AnyKeyword` inside a property type to `JSONValue`, including any `any` that might appear inside a generic argument or a `ts_type` override the generator emits. There is no check that the resulting type is well-formed for the field's declared Go type.
   - It rewrites `source` element accesses to `(source as Record<string, unknown>)` and appends `as string | number | Date` after `new Date(...)` by *text splicing on the raw source*, not by AST node replacement. The `local` edits are computed against `raw` offsets and then re-sliced; this is fragile if the generator ever emits the same substring in a different position. The contract should require AST-node replacement (via `ts.factory` or a printer) rather than string splicing, or explicitly bound the accepted generator output to shapes where splicing is provably unambiguous.
   - The `as ${target}` cast is inserted at the first `" && "` occurrence in the RHS text. That is a heuristic, not a parse. If the generator ever emits a transform with a different operator or spacing, the cast lands in the wrong place. The contract's "fail closed on unrecognised generator shape" is not actually implemented for this case — it silently produces a wrong cast.

3. **`JSONValue` is introduced as a top-level type alias prepended to the file, but the contract does not say what happens if the generator already emits a `JSONValue` or a conflicting name.** The probe prepends unconditionally. A future generator version, or a `ts_type` override, could collide. The contract should require a collision check and a fail-closed path.

4. **G-01 "running normal generation twice produces identical generated bytes" is not the same as "the transform is deterministic."** The probe writes `gotypes.candidate.ts` and `before.js`/`after.js` to the evidence directory. The contract should require that the transform is a pure function of (raw generator output, pinned TS compiler version, transform source) and that the CLI's `--check` compares against the *transform output*, not the raw generator output. As written, `--check` could pass while the transform silently changes behaviour, because the contract does not say what `--check` compares.

5. **G-06 controls are under-specified for the "drop nested conversion" case.** "Drop nested conversion (consumer assertion must fail after compilation)" — dropping a nested conversion in the *generated* file is a hand edit, which the contract forbids. The control must be expressed as a mutation of the *transform* or of the *Go source*, not of the generated output, otherwise the control violates the "no hand modification to generated file" rule. State the mutation site explicitly.

6. **G-05 "keep ordinary frontend tests runnable without a Go installation" is in tension with G-05's "Dedicated generation tests cover the actual CLI."** If the generation tests are part of the default frontend test run, they need Go. If they are not, the contract should say which command runs them and that it is not part of the default `npm test`. As written, both readings are possible.

7. **The strongest objection in the contract is acknowledged but not closed.** "An annotation adapter can drift from its upstream emitter" — the mitigations listed (version pin, reject unsupported shapes, compare emitted JS, retain the unchecked-boundary statement, executable tests) do not include a *drift detector* that fires when the upstream generator's output shape changes in a way the transform still accepts but mis-annotates. The probe's `throw` on unknown shapes is necessary but not sufficient: a new field type that maps to `any` in a new position would be silently rewritten to `JSONValue` without any check that `JSONValue` is the right annotation for that Go type. Add a check that every `any` rewritten to `JSONValue` corresponds to a Go field whose declared type is an interface or `any` (i.e., the wire boundary), and fail closed otherwise.

8. **`Field JSONValue is justified by the Go JSON wire boundary` is asserted, not shown.** The supplied `types.go` has `any` fields (`ToolResultData`, `ToolState`, `Think`) and `map[string]any` (`ApprovalArgs`). The contract should state the rule: `any` in Go → `JSONValue` in TS, and `map[string]any` → `{ [key: string]: JSONValue }`. The probe rewrites `any` to `JSONValue` but does not rewrite `map[string]any`'s value type — it relies on the generator having already emitted `{ [key: string]: any }` and then rewriting the inner `any`. That works for the current generator, but the contract should make the mapping explicit and test it.

9. **No statement of what happens to `ts_type` overrides that contain `any`.** The generator supports `ts_type` tags. If a future field uses `ts_type:"any"`, the transform would rewrite it to `JSONValue`, which may be wrong. The contract should either forbid `any` in `ts_type` or define the behaviour.

10. **The probe's diagnostic check uses `ts.getPreEmitDiagnostics` on a `Program` whose `readFile` is monkey-patched to return the candidate for `codegen/gotypes.gen.ts`.** That is a reasonable experiment, but it does not prove the *real* build (Vite, `tsc -b`, or whatever the project uses) will see the same diagnostics. The contract's G-03 "Typecheck all affected existing application consumers" should name the exact command and config, and the acceptance evidence should be from that command, not from a patched `Program`.

### Strongest objection

The transform is a text-splicing adapter over a pinned generator's output, and the contract's fail-closed claim is weaker than it appears: the probe throws on some unrecognised shapes but silently mis-annotates others (the `" && "` cast insertion, the unconditional `JSONValue` prepend, the `any` → `JSONValue` rewrite without a Go-type check). A future generator bump or a new field shape could produce a file that typechecks, emits identical JS, passes lint, and is still wrong at the annotation level. The contract does not require a check that ties each rewritten `any` back to a Go interface/`any` field, so drift is not detected — it is only detected when the shape is so different that the probe's `throw` fires.

### Safer alternative

Replace the text-splicing transform with an AST-node transform that:
- Parses the raw generator output with the pinned TS compiler.
- Walks the AST and replaces `AnyKeyword` nodes with a `TypeReference` to `JSONValue` only when the corresponding Go field is an interface/`any` (requires the transform to receive the Go type map, or to be driven from the Go side).
- Replaces constructor parameter types and `convertValues` signatures by node replacement, not string splicing.
- Inserts the `as ${target}` cast by locating the assignment's RHS node and wrapping it, not by finding `" && "`.
- Emits via `ts.createPrinter` from the transformed AST, so the output is a function of the AST, not of offset arithmetic.
- Fails closed if any `any` cannot be tied to a Go interface/`any` field, if `JSONValue` would collide, or if the AST contains a node kind the transform does not handle.

This is more code than the probe, but it is the difference between "the current file happens to work" and "the transform is correct for the class of inputs the contract claims to cover."

### Necessary proof before APPROVE

1. Emitted-JS comparison from a real `Program` emit using the parsed `tsconfig.app.json` options (not `transpileModule` with hand-picked options), with the exact command recorded.
2. A drift test: mutate the raw generator output (or the Go source) in a way that changes a field's Go type from `any` to a concrete type, and show the transform fails closed rather than silently emitting `JSONValue`.
3. A collision test: raw output containing a `JSONValue` identifier, showing fail-closed behaviour.
4. A test that every `any` → `JSONValue` rewrite corresponds to a Go interface/`any` field, with a negative case.
5. The G-06 "drop nested conversion" control expressed as a mutation of the transform or Go source, not of the generated file, with the mutation site named.
6. Explicit statement of which command runs the generation tests and whether it is part of the default frontend test run.
7. `--check` semantics stated: what it compares (raw generator output vs. transform output vs. committed file) and what it does on mismatch.

Until these are addressed, the design is a promising experiment, not a bounded maintenance contract ready for production implementation.
