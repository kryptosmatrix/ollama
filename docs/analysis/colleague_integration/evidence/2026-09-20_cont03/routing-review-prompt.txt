8: ## Preamble
9: 
10: TECHNE exists to turn ideas into functioning, testable systems.
11: 
12: This constitution defines the working structure used to move from exploration to release. Its purpose is to prevent ambiguity from travelling downstream until it is accidentally resolved by a prompt, an engineer, or the code itself.
13:

15:

19: 
20: This constitution owns the **lifecycle**: the stages, their order, where each class of decision lives, and how a change propagates. It does not own the gates. Where a stage already has a ratified TECHNE standard — Standard 16 for blueprint promotion, the prompt-pack method for execution, the implementation-proof method for build fidelity, the Reality Gate for conformance — this document names that standard and stops. It never restates a gate's criteria, because two statements of one gate drift apart and then a colleague has to guess which is current.
21:

28: # 1. Governing Principles
29: 
30: ## 1.1 Every decision has an authoritative home
31: 
32: A material decision must be recorded in the artefact responsible for that class of decision.
33: 
34: - Purpose, scope, terminology and hypotheses belong in the concept document.
35: - Architectural choices belong in Architecture Decision Records.
36: - Observable system behaviour belongs in the implementation blueprint.
37: - Execution sequencing belongs in prompt packs.
38: - Actual system behaviour belongs in code and tests.
39: - Acceptance belongs in verification evidence and user sign-off.
40: 
41: A downstream artefact must not silently introduce a decision that should have been resolved upstream.
42: 
43: ## 1.2 Ambiguity must be removed before promotion
44: 
45: An ambiguity exists when two competent engineers could follow the available documentation and produce materially different observable behaviour.
46: 
47: A stage must not be promoted while unresolved ambiguity remains within that stage's responsibility.
48: 
49: ## 1.3 Evidence outranks confidence
50: 
51: Claims of correctness, completion, determinism, compatibility, safety or performance require evidence.
52: 
53: Statements such as "it should work", "the model followed the prompt", or "the implementation looks right" are not acceptance evidence.
54: 
55: This is KANON 4 and KANON 6 stated as a lifecycle rule; the falsifiable-proof obligation and the signal-chain requirement live there.
56: 
57: ## 1.4 Code is not the specification — and code is the truth about what exists
58: 
59: These two claims are both true and they answer different questions. Confusing them is a recurring source of drift, so the boundary is stated here once.
60: 
61: **Code is authoritative about what the system currently does.** When a document and the live tree disagree about present behaviour, the tree wins and the document is corrected. This is the source-authority rule in `TECHNE_AGENT_START.md`, and it is why status labels are audited against source rather than trusted.
62: 
63: **Code is not authoritative about what the system is meant to do.** Behaviour that exists is not thereby approved. When code conflicts with the active blueprint, the conflict is treated as either:
64: 
65: 1. an implementation defect; or
66: 2. a proposed specification change that must be approved and propagated through the documentation chain.
67: 
68: Neither disposition is "the blueprint now says whatever the code does". A running implementation is evidence, not authority.
69: 
70: ## 1.5 Prompt packs do not possess architectural authority
71: 
72: Prompt packs translate an approved blueprint into controlled units of work.
73: 
74: They must not invent requirements, alter system semantics, resolve undocumented architectural questions, or weaken acceptance criteria.
75: 
76: This is KANON 7 stated as a lifecycle rule. The mechanism — including the derived pack-permission token that decides which packs a blueprint's rung licenses — is Standard 16 R-0 and `Method/03_Prompt_Pack_Method.md`.
77: 
78: ## 1.6 Changes propagate from their source
79: 
80: A material change must begin at the earliest artefact whose claims it alters.
81: 
82: The source artefact is updated first. Its downstream effects are then identified, versioned and propagated through dependent artefacts, tests and implementation.
83: 
84: Directly patching downstream work without updating its governing source creates undocumented divergence and is prohibited.
85: 
86: ## 1.7 Human acceptance and technical verification are separate
87: 
88: Technical verification establishes whether the implementation conforms to its specification.
89: 
90: User acceptance establishes whether the resulting system is useful and acceptable in its intended context.
91: 
92: Neither substitutes for the other.
93: 
94: ## 1.8 Release must be traceable and reversible
95: 
96: Every release must identify the exact concept, decisions, blueprint, prompt packs, code revision, verification evidence and acceptance record from which it was produced.
97: 
98: A release without a defined rollback or recovery path is incomplete.
99: 
100: ## 1.9 What has already been paid for must not be paid for twice
101: 
102: Before designing, consult `TECHNE-PA.md` — the Prior-Art & Pitfalls Register — for every artefact the work touches. Published prior art that already solves the problem, and mistakes this project has already made, are both inputs to the design rather than discoveries to be made again during it.
103: 
104: This binds at Stage One and Stage Two, and it is mandatory at Pack 0A (KANON 7). Its reciprocal binds at Stage Ten: a retrospective that surfaced a mistake appends to the register (KANON 16).

28: ## 1. Purpose
29: 
30: Before this standard, the corpus stated obligations for `[IMPLEMENTATION-READY]` through the counterfactual "Pack A can start without architectural questions", evaluated against a monotonically growing document with no mechanical test. The current pointers are `Guides/BLUEPRINT_GUIDELINES.md:120`, `Method/02_Blueprint_Method.md:49` and `Role_Cards/Blueprint_Creator_Rewriter.md:114`; this document now owns the instruments. The earlier corpus also had no termination rule and did not define `BLOCKING`, despite every judge verdict turning on it (`Tools/blueprint-readiness/judge_prompt_template.md:113-117`).
31: 
32: This standard does three things, in this order of importance.
33: 
34: 1. **It gives the top rung instruments, and makes the two top rungs license different actions.** Without differentiated licensing an operator ruling of `[PACK-READY]` withholds nothing, which is how BP81's ten-round grind ended.
35: 2. **It guarantees that judging terminates, and bounds the guarantee at the lineage, not the round.** BP81 ran ten judged rounds with a different-substrate BLOCKING trajectory of 6, 5, 0, 3, 2, 3, 3 and never converged; half its blockers were manufactured by the repairs the judges demanded. A stricter bar without a termination rule makes that worse.
36: 3. **It adds the checks that would have caught the defects that reached production despite blueprints** — arithmetic that cannot produce a non-zero result, structure that cannot represent what the design needs, features nothing reaches, and tests a stub would pass.
37: 
38: **This is not a request for more prose.** NEXUS holds 12,081,416 bytes of blueprint against 233,346 lines of Swift — 51.8 bytes of specification per line of production source. Aevra holds 4,849,932 bytes of architecture against zero production source files. R-3 exists to shrink that, and the rules that add tables (R-6, R-7, R-8) are scoped so they cannot be used to grow it.

42: ## 2. Definitions
43: 
44: ### 2.1 The status ladder
45: 
46: | Status | Exact meaning | Derived pack permission |
47: |---|---|---|
48: | `[CONCEPT]` | A concept document: intended observable behaviour, explicit negative space, deferred decisions. No implementation detail. | none |
49: | `[SPEC-DRAFT]` | Unresolved implementation questions, or failed adjudication. | `PACKS_BLOCKED` |
50: | `[LLD-READY]` | Low-level design complete; frozen requirement set and reach closure published; adjudication not complete. | `PACKS_BLOCKED` |
51: | `[ROOT-ACCEPTED]` | A system-architecture root that allocates ownership and deliberately specifies no mechanism. Governed by R-4, R-5, R-16, R-18 and §6 only. | none; licenses blueprint authoring |
52: | `[PACK-READY]` | Adjudication terminated with bounded residue; §6.5 obligations table present and non-empty. | `PACKS_ALLOWED` — recon and spec packs (0A, 0B, A) only |
53: | `[IMPLEMENTATION-READY]` | Earned by §6.4 `EARNED`. **[PODT-V1]** When the exact amendment payload is externally ratified, it may also be earned by one valid Annex 16A promotion after terminal `OBLIGATIONS`. Self-declaration and closed obligations without valid authority earn nothing. | `PACKS_ALLOWED_FOR_IMPLEMENTATION` — packs A–F |
54: | `[ARCHIVAL]` | Historical record. | none |
55: 
56: **R-0 (structural).** The pack-permission token is **derived** from the effective rung by this table and MUST NOT be authored independently. A document asserting a token above its effective rung is a B1 exhibit, and the derived token is authoritative over any authored one. No gate, role card, template or tool may accept the disjunction `[PACK-READY]` *or* `[IMPLEMENTATION-READY]`; every gate names exactly one effective rung. Existing occurrences at `Guides/BLUEPRINT_GUIDELINES.md:94`, `:257`, `:302` and `:1117` are defects (§9).
57: 
58: **[PODT-V1]** While the exact amendment payload is externally ratified, a valid Annex 16A promotion outcome changes the effective rung; a terminal `[PACK-READY]` header without that outcome does not.
59: 
60: ### 2.1a Live implementation status `[v2.3.0 PROPOSED — NOT RATIFIED]`
61: 
62: Live implementation status is `[FULL]` · `[MVP]` · `[FACADE]` · `Not Yet Implemented`, **and v2.3.0 proposes a fifth, `[DORMANT]`.**
63: 
64: ⚠ **The fifth token is not yet coherent with the corpus and must not be used until it is.** `Method/01_Method_Overview.md:80` reads "Live implementation fidelity labels — **exactly four, and no others**"; `CONSTITUTION.md:121` and `Guides/BLUEPRINT_GUIDELINES.md` §2.2 each enumerate the same four. Adding a token here without amending those three is precisely the one-vocabulary failure §2.1b claims to prevent, and an adversarial reviewer named it as BLOCKING. **Ratifying `[DORMANT]` requires amending all four documents in one change**; until then this section records a proposal and its evidence, not a live rung. `[PARTIAL]`, `[DESIGN]`, `[HLD-READY]`, `[DESIGN-AHEAD-OF-CODE]`, `[OPENER]`, `[IMPL-READY]` are used in the corpus and defined nowhere; they MUST NOT be used.
65: 
66: **`[DORMANT]` — added v2.3.0 (operator ruling, Ash, 2026-08-22).** Implemented, proven by tests a facade would fail, and **not reached in the shipped default configuration**, for one of two reasons which the label MUST distinguish:
67: 
68: - **gated** — the code is wired through the honest production path and a gate defaults closed. It is reachable if a shipped configuration site opens it, and R-10.1 requires that site to be named. `[DORMANT]` here means *not reached by default*, not *unreachable*;
69: - **uncalled** — no production caller reaches it at all. This is **not** "wired through the honest path", and R-9's REACHABLE obligation still binds: an item with no cited chain is `Not Yet Implemented` or a `DEFERRED DESIGN` boundary, and `[DORMANT] (uncalled)` is available only where the code sits on a real path whose sole entry point has no production caller.
70: 
71: A `[DORMANT]` claim MUST carry both of the following, in the blueprint, adjacent to the label:
72: 
73: - **the closer** — the exact gate that holds it shut, cited as `file:symbol` with its default value; or, where the cause is an absent caller rather than a flag, the symbol that has no production caller;
74: - **the opener** — the production emitter that must exist, the configuration site that must set the gate, or the named operator ruling that must be given, before the feature can run.
75: 
76: **R-0.1 (structural).** A feature whose gate defaults closed, or which has no production caller, **MUST NOT be labelled `[FULL]`**. `[FULL]` asserts reachability in a shipped configuration; a gated feature does not have it. A `[DORMANT]` label without both the closer and the opener is a **B4 exhibit** — an undeclared load-bearing symbol, since the gate and the emitter are exactly what an acceptance criterion for this feature depends on, and neither is resolvable to a cited `file:line`. (It is not B2: nothing in the document is refuted by a live site; the site is *missing*.) Mechanically checked by `Tools/blueprint-readiness/dormancy_check.py`.
77: 
78: **Why the token exists, recorded so it is not read as bureaucracy.** A NEXUS audit on 2026-08-22 found eleven subsystems built, wired through `executePulse`, covered by tests, and never executed in the shipped product. None of the four existing values described that state: `[FULL]` was literally true of the wiring and false of the behaviour, `[FACADE]` was wrong because the code and the tests are real, `[MVP]` was wrong because the scope is complete, and `Not Yet Implemented` was wrong because it is implemented. Six blueprints therefore claimed `[FULL]`, and the corpus invented five undefined substitutes — `[DESIGN-AHEAD-OF-CODE]` in 31 files, `[IMPLEMENTATION-READY WITH OPEN QUESTIONS]` in 8, `[PARTIAL-LIVE]`, `[NOT YET WIRED]`, `[ABSENT]`. **A vocabulary gap does not stay empty; it fills with local dialect.** The mandatory closer-and-opener fields are the point of the token: they convert a silent default into a written dependency that a later reader can act on.
79: 
80: ### 2.1b The non-implementation ladder `[v2.3.0 PROPOSED — NOT RATIFIED]`
81: 
82: A document that owns no runtime surface and is not itself a ratified standard or a judge report — a reference, an index, an explainer, a design note — **may** be classified under `Guides/BLUEPRINT_GUIDELINES.md` §2.5 and §2.6, whose ladder is `[DOC-DRAFT]` → `[DOC-READY]` → `[DOC-BLOCKED]`. Two classes are explicitly outside it: a **judge report** carries its verdict plus its own report status per the Guidelines, and a **ratified standard or method document** carries `RATIFIED`, `DRAFT` or `[ARCHIVAL]` — which is why this document carries a ratified v2.2.1 baseline with a separately marked unratified v2.3.0 proposal, while `Method/15` reads `[ARCHIVAL]`, rather than either taking a `[DOC-*]` rung. **That ladder is part of this vocabulary, not a competitor to it**, and is recorded here so `CONSTITUTION.md` §2's statement that TECHNE has one status vocabulary remains true: one vocabulary, two branches, chosen by document class.
83: 
84: `[DOC-READY]` **never** means `[PACK-READY]`. A non-implementation document MUST NOT claim any rung in the table above, any live implementation status, implementation ownership, source or test ownership, or release readiness. A document that does own a runtime surface takes the implementation ladder and MUST NOT take this one.
85: 
86: `[IDEA]` is **not** a promotion rung and derives no pack permission. `Guides/BLUEPRINT_GUIDELINES.md` lists it under design readiness and `Method/02_Blueprint_Method.md` carries it too; both are read here as an intake classification for material that has not yet reached `[CONCEPT]`; it licenses nothing, and a judge meeting it treats the artefact as pre-concept. `Method/01_Method_Overview.md` already records this.
87: 
88: ### 2.2 Proof modes — how a blueprint written before the code discharges a site obligation
89: 
90: Every rule below that demands a site (`file:symbol`, `file:line`) is discharged in exactly one of two modes, and the mode MUST be stated per site.
91: 
92: - **VERIFIED** — the site exists at `source_sha` and the grep returns it.
93: - **DESIGNATED** — the site does not exist yet. The blueprint names the file path to be created, the symbol to be declared, and the owning pack. Pack A converts every DESIGNATED site to VERIFIED against live source, or returns `SPEC_INSUFFICIENT` and stops.
94: 
95: A blueprint may be promoted with DESIGNATED sites; that is the operator's stated process, blueprint before build. A blueprint MUST NOT claim delivered behaviour, `[FULL]`, or a census count on a DESIGNATED site. A judge scoring a site rule NOT-APPLICABLE for want of code is a protocol failure: the correct score is the DESIGNATED form or a finding.
96: 
97: **AS-BUILT.** Where the blueprint documents code that already exists, DESIGNATED is prohibited for any site the code already has, and R-17's failure number MUST be measured **before** the promotion round. A zero, constant or empty result is BLOCKING on its face; it is not a datum to be re-measured later.
98: 
99: **AS-BUILT branches (operator ruling, 2026-08-11).** A blueprint is **as-built** when every behaviour it specifies is already live at `source_sha`, so its production estimate is zero. R-1.1, R-3.1, R-3.2, R-3.4 and §4's third tier question were written for build-facing documents and have no defined value there — 40 × 0 admits no document at all, so every as-built contract was BLOCKING at R-3.2 by construction. They take these branches, and only these:
100: 
101: - **R-1.1.** In place of a cited `[CONCEPT]` document, the blueprint carries the same three things sourced from the system: intended observable behaviour in the operator's terms, an explicit negative-space statement, and the R-17.1 failure number measured on live source before the promotion round. A concept document that does exist MUST still be cited.
102: - **R-3.1 / R-3.2.** The itemised production estimate is replaced by an itemised **documented surface**: every file the blueprint asserts about, with its current line count, summed. The surface is **derived, not declared** — the set of files containing the symbols the blueprint cites under R-4, re-derived by the judge by grep. A file in which the blueprint cites no symbol is not in its surface, so padding the list is self-defeating. The byte ceiling is **4 × documented LOC**, not 40. An absent or undrivable surface is BLOCKING exactly as an absent estimate is.
103: - **R-3.4.** Projected lines equal current lines. A documented file already over the repo ceiling carries an operator waiver or a named successor blueprint — not a split pack, because this blueprint adds no lines.
104: - **§4, question 3.** Read "above 300 LOC" against the documented surface. **A zero production estimate MUST NOT be used to reach Tier 1**; that would put the least build-facing documents, which are often the most load-bearing, under the smallest rule set.
105: 
106: Nothing else branches. R-4, R-16, R-17, R-18, R-19 and §6 apply unchanged, and R-2.2's B2/B4/B5/B6/B7 exhibits remain closure-exempt.
107: 
108: **The ratio is 4, and it is provisional on one measurement.** NEXUS BP01 is 91,891 bytes documenting a 25,807-line surface: **3.56 bytes per documented line**, eleven times tighter than the build-facing 40, because documenting code that exists does not require specifying what to build. 4 is set just above that single observation, so the rule constrains without retroactively failing the document it was measured on. It carries R-3.2's calibration obligation (§10).
109: 
110: **A document proposing any new production work is not as-built.** A mixed document takes these branches only for the sections that are, each marked individually, and itemises an ordinary estimate for the new work. Declaring as-built is a claim under R-4 and needs source evidence; a false declaration is a B2 exhibit.
111: 
112: ### 2.3 Reach closure — the boundary that decides what can block
113: 
114: The **reach closure** of a blueprint is: every file it declares it will create or modify, **union** every file containing a live production producer of any input its specified algorithms consume, **union** every file containing a live production consumer of any output they emit, **union** every file containing a guard on the production write path its data traverses. One hop, enumerated by `file:symbol` in the blueprint and independently re-derived by the judge.
115: 
116: The closure is derived, not declared. A blueprint that omits from its closure the sole production construction site of any input its algorithms consume is BLOCKING under R-2 — that omission is exactly what converts the GSDE defect into someone else's problem.

120: ## 3. Stages
121: 
122: | Stage | Artefact | Exit |
123: |---|---|---|
124: | 1. Concept | `[CONCEPT]` document | R-1 |
125: | 2. Blueprint | Implementation blueprint | §6 adjudication → `[IMPLEMENTATION-READY]` or a terminal exit |
126: | 3. Prompt packs | Pack set 0A–F | R-14 trace, `PACKS_ALLOWED_FOR_IMPLEMENTATION` |
127: | 4. Build and prove | Production code + tests | R-17 reality gate, including the full-system proof |
128: 
129: **The corpus gate (operator's stage 2).** Where the operator requires that all blueprints reach `[IMPLEMENTATION-READY]` before building begins, each blueprint is stamped against its own `source_sha`. *(The corpus-budget precondition this paragraph formerly carried was removed with R-3.3 at v2.2.0.)* A single common corpus `source_sha` is not used: it voids the moment the tree moves, and R-16.2 already scopes the void per blueprint. Each blueprint's Pack A re-verifies its own citations at the then-current HEAD before its build packs run. A corpus gate buys ordering coherence; it does not buy permanent truth.

133: ## 4. Tiers
134: 
135: Answer three questions in the blueprint header. If all three are **no**, the blueprint is **Tier 1**.
136: 
137: 1. Does it introduce or change a persisted type, schema, serialisation or wire format?
138: 2. Does its output cross a repository, process or language boundary?
139: 3. Is its itemised production estimate above 300 LOC?
140: 
141: **Tier 1** discharges R-0, R-1, R-4, R-6, R-12, R-17, R-19 and §6 only, with one judge on a substrate different from the author's, one round, no finding register. **Tier 2** discharges the whole standard. A Tier 1 judge who finds a "yes" to any of the three questions returns `TIER_MISASSIGNED`; the blueprint re-enters at Tier 2 with a fresh budget.

145: ## 5. The rules
146: 
147: Each rule states the obligation, the mechanical test, and the real defect it would have caught.
148: 
149: ### R-1 — Concept and frozen requirement set
150: 
151: **R-1.1** The blueprint MUST cite a `[CONCEPT]` document by path and SHA-256. The concept document MUST carry intended observable behaviour in the operator's terms, an explicit negative-space statement, and the decisions deferred to the blueprint. It MUST NOT carry type declarations, file layouts or pack decomposition.
152: **R-1.2** Every implementation obligation MUST be a numbered requirement carrying exactly one upper-case RFC 2119 keyword and exactly one obligation. The header MUST declare the total count N and the requirement-ID format used.
153: **R-1.3** Prose that is not a numbered requirement carries no obligation, and a judge MUST NOT raise a B1 or B3 finding against it — **but** B2, B4, B5, B6 and B7 exhibits block regardless of numbering (§6.2). Prose describing a live production path MUST be numbered or deleted; relabelling it `DEFERRED DESIGN` is available only for behaviour that is neither built nor specified for this pack series.
154: 
155: **Test.** Cited path exists and its SHA-256 re-derives; the three concept sections are non-empty. Requirement count equals declared N; every line containing an RFC 2119 keyword carries a requirement id; no id appears twice with differing text.
156: **Would have caught.** NEXUS BP04: 47 requirement ids against exactly one RFC 2119 keyword in 1,880 lines, with the whole delta-learning algorithm as un-numbered prose. Aevra: 121 MUST, 46 MUST NOT and 7 SHALL in wholly un-numbered prose across four active documents.
157: 
158: ### R-2 — Reach closure and derived-requirement routing
159: 
160: **R-2.1** Before the first judged round the blueprint MUST publish its frozen requirement set and its reach closure (§2.3), enumerated by `file:symbol`.
161: **R-2.2** A finding anchoring inside the closure or to a frozen requirement blocks on its exhibit. A finding outside both is a **DERIVED requirement**: recorded with an owner and a named successor blueprint, escalated once, not repaired in place, and non-blocking. B2, B4, B5, B6 and B7 exhibits are closure-exempt and block wherever their sites lie.
162: **R-2.3** Re-opening the frozen set is an explicit operator act, recorded. It **consumes** remaining lineage budget (§6.3); it does not reset it.
163: 
164: **Test.** The judge re-derives the closure by grep — construction sites of consumed inputs, read sites of emitted outputs, guards on the traversed write path — and compares it with the published set. Any omission of a sole production construction site is BLOCKING. Findings are then partitioned by set membership.
165: **Would have caught.** BP81: each of ten rounds genuinely closed its predecessor's findings while the zero-guess bar surfaced roughly three new bounded edge cases one seam over; with a declared boundary the judge measures the system rather than the document and the loop is unbounded by construction. And its inverse — a NEXUS blueprint scoped to `Sources/GCDTCore/Learning/` would exclude `Sources/GCDTCore/Integration/GCDTSubstrate.swift:1083`, the sole production construction site of the gradient whose cap makes the arithmetic dead. Under R-2.3 the closure is derived and that file is inside it.
166: 
167: ### R-3 — Volume ceilings (ANTI-BLOAT)
168: 
169: **R-3.1** The blueprint MUST carry an **itemised** production estimate: per pack, per file, with target line counts. A single aggregate number is not an estimate. **An absent estimate is BLOCKING in its own right**, not merely a missing comparison.
170: **R-3.2** Total document **bytes** — the whole file, tables included — MUST NOT exceed **40 × the itemised estimate in LOC**. The ratio is provisional, set below the measured NEXUS baseline of 51.8 bytes per production line, and MUST be recalibrated from measured actuals after the next five promoted blueprints. Exceeding it is discharged only by lossless restructuring or deletion of redundant prose, or by DECOMPOSE after §6.4a independently proves multiple features; never by raising the estimate alone or splitting one feature to escape the ratio.
171: **R-3.3 — REMOVED v2.2.0 (operator ruling, Ash, 2026-08-15; see the changelog).** ~~A repo MUST declare and have the operator ratify a **corpus byte budget** before its first blueprint is stamped, itemised into per-blueprint budgets. Stamping is blocked while the corpus exceeds its budget until the budget is re-ratified on the record or production LOC lands against it.~~ No corpus budget exists; nothing gates a stamp on one. Per-document volume remains governed by R-3.2.
172: **R-3.4** For every file the blueprint will create or modify, it MUST record current lines, projected lines, and the repo's declared ceiling. A file **already** over ceiling MUST carry either a split pack inside this blueprint's own decomposition matrix, sequenced before the pack that adds lines, or an operator waiver carrying a name, a date and the projected count. `DEFERRED DESIGN` is not available to a file already over ceiling.
173: **R-3.4a — the absent-ceiling branch.** A repository declares its hard numeric ceiling in its own `AGENTS.md` or `CLAUDE.md` (`Method/09_Code_Excellence_Method.md` §File Size). **Where the repository declares no ceiling, the ceiling column is recorded as `UNDECLARED` with that citation and the over-ceiling arm of R-3.4 is INAPPLICABLE** — no file can be over a ceiling that does not exist, so no split pack and no waiver is owed by that arm. The rest of R-3.4 still binds and is what the judge scores: **current lines and projected lines MUST still be recorded per file**, and an absent or underived projection is a finding exactly as before. An absent *ceiling* is not. **`[v2.3.0 PROPOSED]`.** The original justification given here was that judges cannot see the branch because it lives in `Method/09`. **An adversarial reviewer refuted that from the estate's own judge record**: `Tools/repository-judge/reviews/blueprints/rounds/de250a4/view/cursor-valid/RESULT.json` returns `CLEAR` with the evidence *"AGENTS.md declares no numeric file ceiling, so R-3.4 follows Method/09:196 and the A1/A2 file split"* — a judge read `Method/09` and discharged correctly. The findings cited as false positives were also **compound**, pairing a real itemisation defect with a ceiling remark. What survives is narrower and is why this clause is still proposed rather than withdrawn: the branch is easier to apply when it sits beside the rule. **It is not evidenced as preventing a measured false-positive rate, and the earlier text claiming so was wrong.**
174: **R-3.5** At pack-series closeout, estimate versus actual is recorded. A lineage whose cumulative estimate exceeds cumulative actual by more than 2× has its R-3.2 ratio halved for its next blueprint.
175: 
176: **Test.** `wc -c` of the document against 40 × the summed itemised estimate; `wc -l` of each named target file against the projected count, and against the declared ceiling **where one exists** — otherwise against R-3.4a. *(The corpus-budget clause of this test was removed with R-3.3 at v2.2.0 and is deleted here; it tested against a budget no repository declares.)*
177: **Would have caught.** Aevra: 4,849,932 bytes of architecture, one code file, zero LOC estimate anywhere in four active documents — BLOCKING at R-3.1 without any argument about ratios (and, before v2.2.0's removal, again at R-3.3 with no ratified budget). NEXUS `StateManager.swift` at 9,692 lines and `NEXUSEngine.swift` at 9,677 — nineteen times the repo's own threshold, reached one approved blueprint at a time.
178: 
179: ### R-4 — Anchored citation
180: 
181: **R-4.1 (judge-enforced, NOT machine-checkable).** Every present-tense assertion about live code MUST carry `file:line`, the exact quoted token relied on, the `source_sha` at which it was verified, and the date. **This obligation is discharged by the judge reading the document, never by a script**, and a rule-coverage row for R-4.1 MUST read `FINDINGS` or `NOT_CHECKED` — never `CLEAR` on the strength of a tool run.
182: 
183: *Amended 2026-07-27. As originally written this rule stated an obligation nothing could verify — the defect this standard exists to eliminate. A checker can only inspect assertions that already took citation shape; a sentence reading "the kernel clamps the budget in LearningKernel" is a present-tense assertion about live code, carries no citation, and is invisible to any mechanical check however perfectly it lexes. Two independent designs reached this conclusion separately. The ambition is kept and its enforcement channel is corrected.*
184: 
185: **R-4.1a (machine-checkable half).** Every assertion that *does* carry a citation MUST satisfy R-4.2 and R-4.3. This is the part a script enforces, and it is the only part a tool may report `CLEAR` on.
186: 
187: **R-4.1b (the promise a citation check makes).** A citation check verifies that **anchors are sound** — the citation lexed, the file resolved, the line is in range, and for an ABI claim the name and value co-occur on one source line. **It does not verify that the blueprint is true.** A false claim whose token happens to appear at the cited line reads as verified, because token presence is the whole of the check. Any tool reporting under R-4 MUST state this limit in its own output, and MUST report every candidate its strict lexer rejected — an unchecked citation that reads as absent is the coverage illusion in §1.
188: **R-4.2** Test citations MUST name a file that exists and a function that exists. The blueprint's declared test-file list MUST be a superset of the test files that reference the symbols in its declared source files, computed by grep.
189: **R-4.3** Promotion FAILS on any citation that does not resolve, or resolves without containing the quoted token. Resolve-rate below 100% blocks.
190: 
191: **Test.** Script the citation list: open each file at each line and string-match the token. The token requirement is what makes this mechanical rather than interpretive.
192: **Would have caught.** BP16's "production cannot transition ARS away from `.disabled`", false at HEAD; the fifteen non-existent test-suite names cited in BP22; BP04, whose two decisive test files (`Phase207_StructuralLearningPipelineTests.swift`, `Run11LearningIntegrationTests.swift`) appear nowhere in it.
193: 
194: ### R-5 — Status floor and coherence
195: 
196: **R-5.1** A label MUST NOT exceed the lowest label of any blueprint the document depends on for a load-bearing behaviour. A document-level label above its own section minimum is permitted **only** if the header enumerates, by section number, every section below it with that section's own label; an unlisted section below the document label is BLOCKING.

329: **Test.** The failure number, unit, instrument and command are present; the judge runs the command on HEAD and records the baseline; at closeout the recorded command matches the declared set or a waiver exists.
330: **Would have caught.** GSDE delta learning emitting exactly zero: a failure number of "sum of absolute committed delta entries after N pulses MUST be > 0" fails on day one, before any judged round, and under AS-BUILT blocks immediately — for roughly 3% of the standard's total cost. The D-9a maintenance sweep declared complete while both its own tests ran with the gate disabled; the NEW-2 checkpoint defect no per-feature test could see; and the recorded incident where a harness reported exit code 0 from the shell pipeline while the compiler never ran.
331: 
332: ### R-18 — Judge independence
333: 
334: **R-18.1** No agent, session or model instance that drafted or repaired any part of a blueprint may emit `BLUEPRINT_JUDGE=PASS` for it.
335: **R-18.2** Judges receive the document text, this standard, **the repo at `source_sha`, every document R-5.2 requires them to open**, the frozen requirement and closure lists, and the finding register (ids, anchors, status only). They MUST NOT receive the author's reasoning, prior verdicts, or prior judges' arguments. **A round whose judge was denied any document R-5.2 requires it to open is `PROTOCOL-INVALID`: it does not count toward the §6.3 budget and MUST be re-run.** Withholding the author's reasoning is correct; withholding the corpus manufactures false CLEARs.
336: **R-18.3** **Blocking requires one judge with a valid exhibit. Passing requires two judges on different substrates, against the same `document_sha` and `source_sha`, each with zero BLOCKING.** Verdicts are never averaged or put to a majority. A same-substrate PASS is never evidence of readiness and MUST NOT count in any round where a different-substrate judge returned findings on the same bytes.
337: **R-18.4** At least one judge's mandate MUST be independent **tracing**: locating declaration sites, persistence and checkpoint paths, async and boundary crossings, write-path guards and the production emitter of every gate. A report whose citations are a subset of the blueprint's own is a citation-verification pass and does not satisfy this.
338: **R-18.5** Findings from all instruments are **unioned**. Agreement is not required and is not sought.
339: 
340: **Test.** The judge artefact records identity, substrate, `document_sha`, `source_sha`, and the context it was given; cross-check against the repair ledger and the lineage `.identity.json` — any name in both voids the PASS. Check the report cites at least one `file:line` the blueprint did not.
341: **Cost.** Two substrates per round is real token and wall-clock cost. **What it buys:** BP81's own natural experiment — the same-substrate judge returned ready for rounds 6 through 10 while the different-substrate judge returned 0, 3, 2, 3, 3 on the same bytes, including a non-existent enum declaration site that would have crashed at runtime.
342: **Would have caught.** The 2026-07-15 NEXUS blueprint that self-declared `[IMPLEMENTATION-READY]` and was judged `NOT_READY` by two independent judges on six convergent findings. BP04's §35, a self-judgement emitted by the same rewrite pass recorded at its own line 1693. Aevra's four adversarial rounds, every one conducted with all four subordinate documents withheld from the judge, which is why three siblings' contradictory self-status survived all four.
343: 
344: ### R-19 — Exhibit-bearing severity and full coverage
345: 
346: **R-19.1** A finding is **BLOCKING** if and only if the judge names its test and supplies the exhibit:
347: 
348: | Test | Name | Required exhibit |
349: |---|---|---|
350: | B1 | CONTRADICTION | Both irreconcilable normative statements quoted |
351: | B2 | IMPOSSIBILITY-AT-SOURCE | A live `file:line` that refutes the instruction |
352: | B3 | UNDETERMINED-OUTPUT | Two conforming implementations exhibited, producing different persisted bytes, public results or digests |
353: | B4 | UNDECLARED LOAD-BEARING SYMBOL | A symbol an acceptance criterion or public signature depends on, neither declared nor resolvable to a cited `file:line` |
354: | B5 | FACADE-PASSES | The twin implementation named, plus the criterion set it satisfies |
355: | B6 | ARITHMETIC-DEAD | A worked extremum showing a formula is constant, saturated or empty over its **producer-attainable** input ranges |
356: | B7 | COMPOSITION-DEAD | An ordered chain of two or more cited `file:line` sites, each individually conforming, whose composition yields a constant, empty or no-op result at the producer-attainable extremum |
357: 
358: **R-19.2** Everything else real is **MAJOR** — non-blocking, but a numbered build obligation bounded under §6.5 — or **MINOR**, advisory. A BLOCKING finding without a named test and exhibit is demoted to MAJOR.
359: **R-19.3** The report MUST contain one row per rule of this standard at the blueprint's tier, valued `CLEAR` (with one line of evidence), `FINDINGS` (anchored, with an exhibit if BLOCKING), or `NOT_CHECKED` (with the reason). `BLUEPRINT_JUDGE=PASS` MUST NOT be emitted while any row reads `NOT_CHECKED`. This coverage record is the input to §6.2's byte-keyed rule.
360: **R-19.4** Judges emitting a foreign severity vocabulary (DEFECT / CONCERN / NOTE, HIGH / MEDIUM / LOW) are **recounted from exhibits, not from labels**: a DEFECT without a B-exhibit is MAJOR, a CONCERN with a B2 exhibit is BLOCKING.
361: 
362: **Test.** Row count equals the tier's rule count; every BLOCKING carries `blocking_test` and `exhibit`; a second judge re-runs only the exhibit — are both quotes present and contradictory, does the cited line say what is claimed, do the two outputs differ, does the extremum recompute, does the chain compose to a no-op. Disagreement then concerns a fact.
363: **Would have caught.** GSDE zero-emission under B6, a two-line calculation no rule ever demanded. The FOUNDRY 58.6% edge drop and the D-9a inert sweep under B7 — the class where every individual site is correct and the chain is dead, which B2 alone cannot exhibit. The 2026-07-15 blueprint's missing per-feature falsifiability structure and dead field, both inside the existing attack list, on a document promoted with no coverage record showing they were ever attacked.
364: 
365: ### R-20 — Finding register and repair containment
366: 
367: **R-20.1** Each blueprint carries one **append-only** register (`<blueprint>.findings.json`). **The orchestrator, not the judge, assigns ids** (`BP81-F-0007`), once, at first appearance, never reused or renumbered; round-local `F-1` numbering is prohibited. **One finding = one B-exhibit anchored to one frozen requirement or closure entry; two findings sharing an exhibit are one.** The orchestrator de-duplicates by exhibit before computing `new_blocking` and publishes the de-duplication as data. Each entry records `first_seen_round`, `first_seen_sha`, `severity_at_first_seen`, `blocking_test`, section, anchor quote, status (`OPEN | CLOSED | OBLIGATION | NARROWED | WITHDRAWN`), `closing_sha`, `introduced_by_sha`.
368: **R-20.2** Every round after the first MUST return, per `CLOSED` entry whose anchor still exists, either `CONFIRMED_CLOSED` or `REOPENED` with a quote. A missing entry is a protocol failure and the round is re-run.
369: **R-20.3** Every repair round MUST produce a **carry-over audit**: one row per previously-closed finding (`STILL-CLOSED` / `REOPENED`) and one row per load-bearing item — type, constant, field, formula, invariant, criterion id — marked `KEPT`, `CHANGED-with-reason` or `INTENTIONALLY-DROPPED-with-sign-off`. A repair that cannot enumerate is not a repair. This applies to status-only patches: a patch that enumerates four corrections without enumerating the population it drew them from is not a repair.
370: **R-20.4** A repair round MUST change only the sections named in the findings it discharges; a heading changed outside that set voids the round. A repair that touches one member of a document family without emitting R-5.3's family table also voids the round.
371: **R-20.5** A repair round adding more than **150 lines** requires operator approval before the next round is dispatched. Content mandated by R-6, R-7.2, R-8.1 and R-12.1 is **exempt** from that trigger: the growth budget must not tax the rules that carry the standard's protective value. Closing a finding by **deleting or narrowing** an unhonourable claim is a first-class closure, recorded `closed_by: NARROWED`, and is preferred whenever both close the finding. Each repair commit closes exactly one register id and names it in the subject.
372: **R-20.6** The judge report field is `required_property` — the determinacy or invariant the document must acquire — not `required_fix`. A judge MUST NOT prescribe a mechanism, and a repair agent MUST NOT treat a prescribed mechanism as authority.
373: 
374: **Test.** Diff the register between rounds: no id changes meaning, none reused, every `CLOSED` carries a `closing_sha` and appears exactly once in the next report. `git diff` the blueprint: changed headings ⊆ headings cited in the discharged findings; insertions − deletions > 150 requires a recorded approval. Scan `required_property` for imperative design verbs.
375: **Would have caught.** BP81's round 6→7 regression: round 6 reached 0 BLOCKING, then its own +259-line repair created a routing-without-apply crash window and dropped `trainingPermissionRaw` from the registry digest, going back to 3. The round-6 silence: round 5's report already contained the round-7 defect verbatim, the repair fixed only half, round 6 raised nothing, round 7 re-raised it BLOCKING — one full round lost for want of a register. Two judge-prescribed defects: round-6 F-7 ordered the split that became round-7 F-3; round-7 F-4 ordered the propagation that became round-10 F-2.

379: ## 6. Termination
380: 
381: ### 6.1 Definitions
382: 
383: An **adjudication** is an ordered sequence of judged rounds over one blueprint, each against a frozen `document_sha` and `source_sha`. `new_blocking(N)` is the count of BLOCKING findings registered in round N not already in the register — a set difference over the append-only register, computed by the orchestrator after exhibit de-duplication (R-20.1), with no judgement involved.
384: 
385: ### 6.2 Admissibility
386: 
387: - A finding MUST anchor inside the reach closure or to a frozen requirement, or it is DERIVED and non-blocking (R-2.2).
388: - A finding MUST carry a B1–B7 exhibit to be BLOCKING, or it is MAJOR (R-19.2).
389: - **Precedence.** B2, B4, B5, B6 and B7 exhibits block regardless of (a) whether the text they cite is numbered, (b) whether the sites they cite lie inside the declared closure, and (c) when they were first noticed. A fact about live source or about what the criterion set admits does not become less true for having been missed once, nor for being described in prose the author chose not to number.
390: - **Byte-keyed rule.** A **B1 or B3** finding first raised in round N against text unchanged since round N−1's `document_sha` is admissible only as MAJOR — **and only where round N−1's coverage record (R-19.3) reads `CLEAR` for the rule under which it is filed.** Where round N−1 read `NOT_CHECKED` or did not cover that section, the finding keeps its exhibit-derived severity. Reader variance is a discriminator only where the earlier reader actually looked.
391: - **Regressions always block.** A finding whose `introduced_by_sha` falls inside this adjudication's repair range blocks, must be closed before pack authoring, and is exempt from the byte-keyed rule.
392: 
393: ### 6.3 Budgets
394: 
395: - **Lineage budget: 8 judged rounds per blueprint id**, spanning every adjudication, re-adjudication after REJECT, and scope re-open. A scope re-open **consumes** budget; it does not reset it. When the lineage budget is exhausted the only permitted exits are EARNED, OBLIGATIONS, DECOMPOSE or terminal REJECT — never another round.
396: - **Per-adjudication cap: 5 rounds.** Round 6 of an adjudication does not exist.
397: - **Ratchet:** for any N ≥ 3, if `new_blocking(N) > 0` **and** `new_blocking(N) ≥ new_blocking(N−1)`, the adjudication ENDS at round N. A zero-zero sequence is convergence, not failure: it routes straight to the EARNED check with no escalation.
398: - Tier 1 (§4) has a budget of one round.
399: 
400: ### 6.4 The four terminal exits
401: 
402: | Exit | Precondition | Result |
403: |---|---|---|
404: | **EARNED** | Two judges, different substrates, same `document_sha` and `source_sha`, zero BLOCKING each; zero open regressions; **at most 5 open obligations, each bounded per §6.5** | `[IMPLEMENTATION-READY]`, `PACKS_ALLOWED_FOR_IMPLEMENTATION` |
405: | **OBLIGATIONS** | At most 5 residual BLOCKING findings, every one bounded per §6.5 | `[PACK-READY]`, `PACKS_ALLOWED`; header states `[IMPLEMENTATION-READY]` was NOT earned |
406: | **DECOMPOSE** | Every required judge — one at Tier 1, two at Tier 2 — satisfies the feature-boundary test below against the same matrix and operator approves the child set | Children declared; parent → `[ARCHIVAL]`; each child gets its own 8-round lineage budget |
407: | **REJECT** | §6.4a does not earn DECOMPOSE, and either the tier's required judge panel unanimously places the earned level two or more rungs below declared, residue exceeds 5, any residual is unbounded, or one section produced BLOCKING findings in three consecutive rounds | `[SPEC-DRAFT]`; rework starts from the judge reports, not the current text; if budget remains, whole affected sections and their seams may be reconciled under the same id; at zero remaining rounds this is terminal |
408: 
409: Decomposition is permitted **once per blueprint lineage**. A child that would decompose again exits via OBLIGATIONS or REJECT.
410: 
411: **Exit precedence is deterministic:** DECOMPOSE if and only if §6.4a is earned and operator-approved; otherwise REJECT if the tier's required judge panel unanimously places the earned level two or more rungs below declared; otherwise EARNED; otherwise OBLIGATIONS; otherwise residue- or trajectory-based REJECT. EARNED therefore dominates historical recurrence, not an explicit unanimous rung rejection. The stronger stamp may never carry the larger backlog: the same cap, boundedness requirement and §6.5 table apply at EARNED and OBLIGATIONS. Residue above five or any unbounded residual prevents both.
412: 
413: ### 6.4a Feature-boundary test
414: 
415: A proposed child is a feature, rather than an implementation component, only if all are true:
416: 
417: 1. it produces an operator-visible outcome meaningful without its siblings;
418: 2. it has its own failure number rather than merely causing the parent outcome to fail;
419: 3. it can be accepted, released, deferred or rejected without leaving its siblings as an incomplete version of one outcome; and
420: 4. removing sibling implementations still leaves the child's acceptance criteria satisfiable through its declared public inputs and outputs, rather than through an unfinished internal seam.
421: 
422: Every required judge's existing `section-6` coverage evidence begins with exact token `FEATURE_BOUNDARY=SINGLE_FEATURE;` plus one evidence clause of at most 90 characters against the blueprint's stated outcome and failure number when no child set is proposed. This is evidence inside the existing 128-character coverage row, not a new result-schema field. If the author or any judge proposes children, the author publishes one candidate-child matrix with evidence for all four rows and every required judge begins that same coverage cell with `FEATURE_BOUNDARY=MULTI_FEATURE;` or `FEATURE_BOUNDARY=SINGLE_FEATURE;` after scoring the matrix. DECOMPOSE is earned only when all required reports — one at Tier 1, two at Tier 2 — carry `MULTI_FEATURE`; the orchestrator publishes their union and the operator approves the exact finite child set. A Tier 2 disagreement yields `SINGLE_FEATURE` and no child budget. The operator may re-open scope for another counted adjudication, but that later adjudication still requires all required `MULTI_FEATURE` tokens against one matrix before DECOMPOSE.
423: 
424: If all proposed children are required to produce one outcome, they remain components of one blueprint and become ordered prompt packs. Module, process, worker, OAuth, security, persistence, file-custody and test/reality-gate boundaries justify serial packs and explicit interfaces; they do not establish separate features by themselves. Residue count and review history require more detail, not synthetic children.
425: 
426: After REJECT, repair is holistic when budget remains: reconcile every affected section and its inbound and outbound seams, then publish a complete requirement-to-pack matrix naming component ownership, interfaces, dependencies, exact source/test custody, proof and stop conditions. Local finding patches do not qualify. At zero remaining rounds REJECT is terminal; the blueprint stays `[SPEC-DRAFT]` or is separately archived as a historical record, and it does not split merely to reset the budget.
427: 
428: ### 6.5 Bounded obligations
429: 
430: An obligation is **bounded** only if it names an owning pack, a named check and a falsifier. The obligations table carries one row per residual finding — register id, grade, blueprint section, unresolved question, what the recon pack must do, owning pack — plus these three clauses verbatim:
431: 
432: > Pack A (recon) MUST resolve each obligation below against LIVE SOURCE and record the resolution with `file:line` evidence, or return `SPEC_INSUFFICIENT` to this blueprint and stop.
433: > No build pack may close `[FULL]` while any obligation below is open.
434: > Every DESIGNATED site in this blueprint is converted to VERIFIED by Pack A, or returns `SPEC_INSUFFICIENT`.
435: 
436: This relocates residue to the one place it can be settled — live source, where a guard either exists with a falsifier that fails without it, or it does not.
437: 
438: ### 6.6 The guarantee, stated honestly
439: 
440: Every blueprint id consumes at most 8 judged rounds across all adjudications. Decomposition is permitted once only after §6.4a proves a finite child set; children cannot decompose again. **Total judged rounds over a true multi-feature lineage is therefore bounded by 8 × (1 + K), K the approved child count — finite and known before child adjudication begins. A single feature remains bounded at 8.**
441: 
442: This guarantees the **ordinary design process** terminates. It does not guarantee promotion. A blueprint may exhaust its budget and exit at `[PACK-READY]` with bounded obligations, enter an approved true-feature decomposition, or terminate at REJECT. Later obligation closure grants no implementation permission by itself. Later archival alone grants no budget or pack permission.
443: 
444: **[PODT-V1]** While the exact amendment payload is externally ratified, one Annex 16A transition may verify the exact frozen residue after `OBLIGATIONS`. It has its own one-use opening and two-panel-round ceiling, constrains both blueprint and behaviour-influencing source deltas, cannot perform design work and does not reset the ordinary budget.

446: ### 6.7 Retrospective tests against two BP81 lanes
447: 
448: NEXUS BP81 different-substrate BLOCKING trajectory: r4 = 6, r5 = 5, r6 = 0, r7 = 3, r8 = 2, r9 = 3, r10 = 3.

453: - The **byte-keyed rule** demotes round-7 F-1 (unchanged text, a contradiction) to a build obligation **only if** round 6's coverage record read CLEAR for that rule; round 6 raised nothing at all, so if it recorded `NOT_CHECKED` the finding keeps its severity. It does not touch round-10 F-3, which cites live source.
454: - Under R-2's derived closure the adjudication converges at round 6 with a disclosed, owned gap list and an earned stamp.
455: 
456: AGORA BP81's ClickUp connector later exposed the boundary defect directly. Its proposed broker core, OAuth worker, MCP/reporting surface and reality gate were all necessary for one operator-visible outcome; none could be accepted or released as that outcome without the others. Two different-substrate round-4 judges then returned zero BLOCKING against the same technical candidate. The earlier rule nevertheless required BP82–BP85 solely from blocker history. Under §6.4a they are serial component packs inside BP81, while the clean current panel controls EARNED and the historical trajectory remains evidence for the pack detail required.
457: 
458: The rule shortens the process without laundering a defect that is a fact about source, about arithmetic, about composition, about an undeclared symbol, or about what the criterion set admits.
459: 
460: ### 6.8 Post-obligation discharge transition `[PODT-V1]`
461: 
462: This section is inactive unless the exact `PODT-V1` amendment payload is externally ratified. When `OBLIGATIONS` is the terminal ordinary exit and Pack A later closes the exact bounded obligation set against independently authorised live source, the blueprint remains `[PACK-READY]` unless one post-obligation transition passes Annex 16A in full.
463: 
464: That transition is verification, not another design adjudication. It opens once, binds retrievable terminal objects, measures and classifies both blueprint and behaviour-influencing source deltas, executes every closure check and falsifier, and rejects unauthorised source changes, new scope, design choices, id or reach changes, feature-boundary changes, failure-number changes and substantive defects. The tier's complete fresh independent panel must return zero BLOCKING, MAJOR and MINOR findings with no unchecked lens. A committed panel start consumes one of two panel rounds even if a judge crashes or returns protocol-invalid. Every accepted attempt must be launched through a qualified one-use causal harness whose external audit binds that already-committed start, the canonical request, the exact extracted report bytes and the complete attempt population; a report committed later is not sufficient evidence by itself. TECHNE's own judged amendment payload remains byte-frozen in both committed and directly hashed working bytes through external ratification and active use, apart from the separately verified append-only register. Its method-review transport observation binds the report bytes internally but is not itself an attestation; the operator must verify the named external record outside the recorder's authority.
465: 
466: Only the external append-only `POST_OBLIGATION_DISCHARGE_PROMOTION` outcome defined by Annex 16A changes the effective rung to `[IMPLEMENTATION-READY]`. Closing rows, editing the header, writing a pack or recording an override does not. The outcome is prospective, cannot authorise earlier source or build work retroactively and is revalidated with the whole authority chain at every implementation-pack boundary.

1: # 04 - Implementation And Proof Method
2: 
3: Last updated: 2026-09-16
4: 
5: The implementation method is built around `[FULL]` or stop. It treats production code as complete only when the feature is wired through the real path and proven at the right depth. Compilation is necessary, but it is never enough for a runtime claim.
6: 
7: For serious work, `[FULL]` is necessary but not sufficient. The code must also satisfy the excellence bar in `Method/09_Code_Excellence_Method.md`.
8: 
9: ## The Prime Directive
10: 
11: Default to `[FULL]`.
12: 
13: If `[FULL]` cannot be reached in the current scope, complete the longest dependency-safe prefix that can reach `[FULL]`, then stop cleanly. Do not ship `[MVP]` without explicit approval. Do not ship `[FACADE]`.
14: 
15: `[FULL]` requires:
16: 
17: - production code;
18: - honest-path wiring;
19: - meaningful tests;
20: - at least one stub-fail test;
21: - at least one facade-path proof for each feature, with executed fault-detection evidence;
22: - the Test Discipline And System Acceptance Gate below for every runtime feature;
23: - build/test proof with full outputs and exit codes;
24: - zero new warnings;
25: - no placeholders on active paths;
26: - tight diff;
27: - proof bundle.
28: 
29: Excellence requires:
30: 
31: - minimal and appropriate public surface;
32: - strong invariants;
33: - clear ownership boundaries;
34: - simple and traceable data flow;
35: - efficient and appropriate algorithms;
36: - bounded resource use;
37: - good naming;
38: - low coupling and high cohesion;
39: - graceful failure;
40: - composability;
41: - maintainability;
42: - deletion of accidental complexity;
43: - APIs that feel natural and hard to misuse.
44: 
45: ## Pre-Flight
46: 
47: Before non-trivial implementation, record:
48: 
49: 1. Spec located and read by section name.
50: 2. Live baseline captured.
51: 3. Honest write path identified.
52: 4. Falsifiable contract stated.
53: 5. Out-of-scope named.
54: 6. Stop conditions listed.
55: 7. Quality bar and craft risks stated.
56: 8. Detail ledger opened or updated for exact types, constants, APIs, lifecycle states, edge cases, tests, failure modes, migrations, and integration points.
57: 9. Engagement mode chosen.
58: 
59: The falsifiable contract must name the test or proof that would fail a fake implementation. Before implementation, record the production assembly and input producers, requirement-derived expected outcomes, existing regression obligations, applicable fault controls, and canonical acceptance commands. Use `Templates/Feature_Acceptance_Evidence.md` as the evidence record; an existing equivalent record is acceptable if it preserves every required field.
60: 
61: ## Honest Code Path
62: 
63: Every state mutation, side effect, persisted record, event, proposal, API call, job, or runtime behaviour must use the codebase's existing path for that class of operation.
64: 
65: If the honest path is missing a hook, extend it minimally. Do not create a side channel.
66: 
67: Examples of dishonest paths:
68: 
69: - writing directly to storage when the codebase uses a repository, reducer, or state manager;
70: - mutating state in a test helper instead of the production entry point;
71: - calling a subscriber directly instead of publishing through the event system;
72: - filling a cache by writing its backing file instead of the cache writer;
73: - bypassing reducer validation because tests are easier.
74: 
75: Tests should exercise the honest path. A test that bypasses production routing cannot prove production routing works.
76: 
77: ## Acceptance Tests
78: 
79: Implementation starts by extracting requirements and acceptance criteria.
80: 
81: Required categories when applicable:
82: 
83: | Category | Purpose |
84: |---|---|
85: | Happy path | Intended use. |
86: | Boundary | Empty, max, off-by-one, threshold, over-cap, under-cap. |
87: | Negative/failure | Invalid input, missing precondition, illegal transition. |
88: | Facade-fail | Most likely fake implementation fails. |
89: | Integration | Entry point to real consumer. |
90: | Persistence/reopen | Stored state survives and is functionally used after reopen. |
91: | Determinism/replay | Same seed/input produces identical output. |
92: | Disabled mode | Feature-off behaviour matches spec. |
93: | Migration/backward compatibility | Old data or old contracts still work when required. |
94: 
95: The central rule: if a no-op implementation passes all tests, the tests do not prove the feature.
96: 
97: ## Test Discipline And System Acceptance Gate
98: 
99: This section is the canonical testing contract for TECHNE. Role cards, prompt packs, templates and repository test contracts apply it; they must not replace it with a weaker local checklist. It strengthens the existing honest-path, activation and facade-fail obligations without changing blueprint-promotion rules, runtime permissions or release authority.
100: 
101: > No runtime feature may be accepted as complete until automated tests exercise its normal production entry point, prove that its required data reaches it, verify the specified downstream outcome, and demonstrate that relevant broken implementations are detected. Existing supported behaviour must remain protected by regression tests.
102: 
103: ### T-01 — Test at several levels; accept at the system boundary
104: 
105: Every test must protect a named behaviour, invariant, failure mode or regression. Keep focused unit and integration tests for precise diagnosis. Every new or changed runtime feature additionally needs end-to-end acceptance scenarios covering its claimed requirements, plus the established system regression suite. A large test count, line coverage, compilation or helper-only tests cannot discharge this obligation.
106: 
107: End-to-end means the complete production path from the real ingress, through production assembly and data processing, to the final consumer and specified observable result. State the system boundary before designing the test. Do not shrink it after a failure to omit the broken connection. Cross-repository runtime claims include the real inter-repository boundary and identify every participating revision.
108: 
109: A standalone library may prove its own public contract at that boundary; this does not prove that a consuming application invokes it. A pure algorithm or documentation-only change does not need an invented application launch. Its proof must match its actual claim, and affected runtime consumers still need regression coverage. No finite suite guarantees the absence of every defect; completion is scoped to the recorded requirements, scenarios and environments.
110: 
111: ### T-02 — Production must assemble the feature, not the test
112: 
113: Acceptance must start the application, service, CLI or runtime through its normal bootstrap and dependency assembly, with the real registrations, routing, feature flags, configuration loading and lifecycle. Manually constructing and connecting the new component proves only that manual assembly.
114: 
115: Do not call a worker, subscriber, reducer or learner directly when the claim is that the scheduler, event bus, application or runtime invokes it. Do not seed the expected output, fill a downstream cache, pre-create learned state or mutate authoritative state to bypass the transition under test. Fixture setup may establish declared unrelated preconditions; it must not supply the wiring, data transfer or outcome the test claims to prove.
116: 
117: A headless harness is acceptable only when it uses the same production assembly and relevant lifecycle. Record what it omits and why that omission does not remove an obligation. UI-specific interaction claims still require the real UI route. At least one applicable startup/configuration smoke must exercise production defaults; test-scale overrides must be enumerated, preserve the claimed semantics and not manufacture reachability by changing thresholds, ordering or permissions.
118: 
119: ### T-03 — Required data must arrive, be usable and affect the result
120: 
121: Trace each required input from its real producer, through transport and any conversion, to the feature and its downstream consumer. State payload identity, shape, units, valid range, availability/freshness and ordering where relevant. Observe actual delivered values rather than only the requested configuration or a call counter.
122: 
123: Use contrasting valid inputs with requirement-defined outcomes to reject constant-output and ignored-input implementations. The variation must enter upstream of the connection being proved. Exercise producer-attainable values, not artificially enlarged signals that cross a threshold production can never reach. Where production uses files, models, corpora or stored records, include a representative real-format fixture through the normal loader; identify its provenance and the limits of toy or synthetic evidence.
124: 
125: Test missing, empty, stale, malformed, out-of-range and misordered inputs where the contract makes them relevant. Assert the specified rejection, abstention, retry or recovery and the absence of forbidden success. Include a valid positive case so an always-rejecting implementation cannot pass solely on negative tests.
126: 
127: ### T-04 — Assert the specified outcome independently
128: 
129: Derive expected results from the approved requirement, independently calculated vectors, a separately justified reference, or a stated property. Do not use the production function under test to calculate its own expected answer. Do not update a golden result merely because the new code disagrees; establish whether the code, fixture or specification is wrong and record any approved change.
130: 
131: A returned success flag, emitted event, log, non-empty object, non-zero gradient or changed digest is supporting evidence, not proof of the intended effect. Verify that the real consumer produces the required outcome. For a no-change requirement, assert the specified invariant and demonstrate that a prohibited change is detected. Where logging or reporting is itself the requirement, validate the record's contents against the underlying event or state.
132: 
133: For learning claims, distinguish acquired-state change from useful learning: prove subsequent behaviour uses the acquired state, persistence and selective removal where claimed, and held-out benefit against the declared controls when improvement or generalisation is claimed. A training-loss change alone must not be promoted into a system-learning claim.
134: 
135: ### T-05 — Execute deliberate-break controls
136: 
137: A statement that a test *would* fail is a plan, not fault-detection evidence. For each feature, run the relevant unchanged acceptance assertions against an isolated deliberately broken implementation. Cover a no-op or fixed-output implementation and each applicable critical failure class: missing registration/dispatch, interrupted or corrupted required data, and a disconnected downstream consumer. Record a reviewed reason for an inapplicable class; an inconvenient or unavailable experiment is not inapplicable.
138: 
139: For each control, first show the unmodified implementation passes the named scenario; introduce one identified fault; show the expected behavioural assertion fails; then run the clean implementation again and show it passes. Retain the fault patch or injection configuration, test identifier, actual exit status and failure output. Prove that the fault was active in the tested path. A compilation error, unrelated exception, missing dependency, generic timeout or zero collected tests does not count as detecting the intended fault. A timeout counts only when bounded completion is the requirement and the missing required effect is specifically established.
140: 
141: Keep faults in disposable copies, isolated test processes or explicitly scoped test seams. Never mutate a shared production installation, live data or another colleague's work to conduct a control. Never weaken the assertion for the broken arm or leave a fault enabled in the accepted artefact. Retain these controls so repairs and future changes can re-run them. Test doubles are permitted in the deliberately broken arm; they must not silently replace the real positive arm.
142: 
143: ### T-06 — Regressions, lifecycle and compatibility are part of acceptance
144: 
145: Capture the existing baseline before changing behaviour and run the established regression suite after the change. Include neighbouring consumers and shared assembly, configuration, state, persistence and routing paths affected by the diff. Reuse existing acceptance scenarios where they cover the requirements; add missing system-level coverage rather than wrapping every unit test in a full launch.
146: 
147: Preserve supported behaviour, not known defects. Record intended behavioural changes and their authority. A baseline failure must remain visible; unchanged failure is not success. It cannot discharge an acceptance obligation for the changed feature. Do not delete, skip, weaken or rebaseline a failing test merely to recover green status.
148: 
149: Exercise relevant boundaries and lifecycle: first startup, repeated use, shutdown/restart, cancellation, recovery, migration and resource limits. Test feature-off semantics where the feature is gated. For process-surviving persistence, terminate the writer and prove a fresh process restores and functionally uses the state. Reusing an in-memory object is insufficient.
150: 
151: ### T-07 — Declare simulated boundaries and control nondeterminism
152: 
153: The positive acceptance path must use the real internal components and connections whose integration is claimed. Mocks and spies remain useful for focused tests and diagnosis, but a mock replacing the component or link under claim cannot establish its production integration.
154: 
155: An external service may be simulated for hermetic tests when the contract and substitution are explicit. Such a run proves behaviour against that simulation, not live-provider compatibility. A claim about the real external service additionally requires an authorised sandbox or real-service contract test. Do not use live credentials, incur charges, send messages or modify real user data merely to make a test end-to-end; existing permission boundaries still apply.
156: 
157: Record seeds, clocks, scheduling controls, dependency versions, platform, artefact identities and test configuration. Prefer observable completion and bounded waits over arbitrary sleeps. A deterministic-core claim requires canonical equality on repeated execution; a probabilistic or performance claim requires a predeclared metric, threshold, repetitions and variability treatment. Retain every attempt. Do not retry until green and discard the failures.
158: 
159: ### T-08 — Required acceptance must actually run and fail closed
160: 
161: Each adopting repository must name its canonical test and system-acceptance commands, required scenarios, supported execution environments and the default validation or required pre-merge/release jobs that execute them. Runtime activation coverage must not exist only behind an optional slow/integration flag excluded from acceptance. Separate jobs and specialised runners are allowed; all required jobs must complete for the exact candidate being accepted.
162: 
163: The acceptance runner must propagate failing child exit statuses and verify expected test discovery and completion. In the clean acceptance/regression runs, missing required tests, zero collected cases, skipped/disabled/expected-failure obligations, swallowed errors, unavailable dependencies, stale reports and interrupted runs are not passes. The deliberately broken arm of T-05 is different: its enclosing control succeeds only when it verifies the specifically expected failure and the clean arms pass; an expected-failure annotation must not hide missing positive behaviour. A shell log command such as `; echo "exit=$?"` prints a status but can itself return zero: retain the real child status and make the gate return failure when it fails.
164: 
165: Use the repository's existing runner and result format, not an unnecessary second framework. A gate that validates a report's fields or hashes proves record integrity only; it must not turn an implementer's self-authored `PASS` into runtime evidence. Test the runner itself with a failing child, a missing required case and an empty selection, and verify that each blocks acceptance.
166: 
167: If the required environment or gate is absent, record the exact missing obligation and withhold `[FULL]`, `JUDGE=PASS` and `GATE=PASS` for the affected runtime claim. Record a narrower completed scope only if it is genuinely independent; do not rename a disconnected feature to make it complete. These method requirements do not install hooks, change branch protection or authorise edits to other repositories. Adoption and automated enforcement must be verified per repository; reading this document is not deployment evidence.
168: 
169: ### T-09 — Bind requirements to retained execution evidence
170: 
171: Use `Templates/Feature_Acceptance_Evidence.md` or an equivalent record. Every claimed requirement must map to its source, production entry/assembly, data producer, consumer, expected observable, named tests, applicable deliberate-break controls and actual results. Record the scope and any omitted boundary explicitly.
172: 
173: The bundle must identify the tested commit and working-tree delta, all participating repository revisions, build/artefact and fixture identities, configuration, commands, full retained output, actual exit codes, discovered/executed/failed/skipped counts and all attempts. A timestamp or commit alone is insufficient when uncommitted code influenced the run. Missing or truncated evidence is incomplete until the remainder is retrieved; summaries may point at retained full logs but must not replace them.
174: 
175: Retain the evidence at a durable project path and make it discoverable from the requirement or completion record. A changed implementation, acceptance assertion, fixture, required dependency or relevant configuration invalidates affected evidence and requires re-execution before acceptance. Preserve failed runs and fault-control results rather than overwriting them with the final success.
176: 
177: ### T-10 — Review the tests as well as the implementation
178: 
179: The reviewer must inspect actual production assembly, input provenance, assertions, observed fault failures and test-runner inclusion, not just the report labels. Independently re-run the required acceptance and regression commands against the candidate under review; reproduce the applicable deliberate-break controls in isolated copies. Independence requirements elsewhere in TECHNE still apply.
180: 
181: Use existing verdicts. Missing, blocked or not-run mandatory evidence prevents a passing completion verdict; it is not a new flavour of pass. Record unresolved obligations with owners and exact next commands. When repairing an existing disconnected or data-starved feature, add a regression scenario that fails on that defect through the real path before closing it.

324: 		}
