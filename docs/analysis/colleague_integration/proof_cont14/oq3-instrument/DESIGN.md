## What it measures

G1's failure number is "incorrect instruction deliveries per controlled conversation", over save/restart/new, edit/continue, explicit reload, disable, terminal reset and compaction; any value above zero fails G1 (blueprint line 18). The instrument publishes

    failure number = (bad observed deliveries + missing required deliveries) / controlled conversation trials

with its components, per-category counts (overlapping; one bad request counts once in the numerator), per-family and per-trial breakdowns, operation and refusal verdicts, **auxiliary checks** (summariser requests, preloads, leaks, requests the real daemon refuses for their method) and **a separate validity verdict**. A zero numerator is not acceptance: the run must be valid, every auxiliary check must pass, and every operation must pass on its own evidence.

## Boundary

The capture point is the inference daemon's input: a fake daemon at `OLLAMA_HOST` records every request on every path, with its method, raw request target, query string, `Host`, headers and trailers (credential-shaped values are stored redacted; the instruction scan reads them unredacted as they arrive). Three arms reach it, each in its own OS process: the real `app/ui.Server.Handler`, assembled as `app/cmd/app/app.go:208-287` does (restart = SIGTERM, observed exit, new process on the same `HOME`); `launchInteractiveModel` → `GenerateAgentTUI` → `agentchat.Run` on a real pseudo-terminal (the function the launcher's run-model action calls, `cmd/cmd.go:2242`), with CLI steps through the real root command; and the built `ollama` binary with no arguments, through the launcher menu and model picker (E1).

Declared simulations: inference is the fake daemon (scripted replies; `read` tool calls where a turn asks; a summary for the compactor; injected failures, held responses and a high prompt count where declared; `chat.admission.v1` advertised, except in D11 and T10; an A9-shaped `admission` object returned to a request that carries the field). The fake answers each known path only with the methods the real daemon's route table registers (`server/routes.go:1859-1891`, `HandleMethodNotAllowed` at `:1852`) and 405 otherwise, as the real daemon does. Declared omissions: the desktop's embedded daemon, MCP manager, updater and webview; on the lifecycle arm, the launcher's heartbeat, menu and model resolution (the entry arm covers them). A closed-port proxy blocks every non-loopback HTTP(S) request from the children.

## The ledger

`oq3_scenarios_test.go` freezes 27 scenarios and 39 trials (the run prints the ledger's SHA-256). Every step is a **required dispatch** (one expectation per model request it must cause, tool continuations included), a **required no-dispatch** (A12: no carrier-bearing request may be sent to a daemon without the capability), a **required refusal**, a production **operation** with an expected outcome, or a **harness** action. Designated surfaces absent before G1 are attempted in their designated form and their real responses recorded; later steps run anyway; no expectation is weakened because a save failed. A harness failure makes the run invalid; the steps it stops (and a held turn whose completion failed) are recorded as not measured and never enter the number.

State-changing steps assert their effect on the frozen pre-G1 request: the tool count after the `/tools` toggle, the model after a switch, the presence of the system message after `/system off|on`. A scenario that does not reach its declared state is invalid.

Coverage: desktop D0–D11 (unconfigured controls; save/restart/new; edit while continuing; reload and idempotent reload; disable, restart while disabled, restore and reset; a legacy transcript with revision zero and adoption; restart and reopen; binding timing for a pre-allocated ID; a failed first turn, its retry and a new ID; a held turn with a concurrent save from another process and a refused reload; web-search tools and a model change; a capability-less daemon). Terminal T0–T10 (unconfigured controls; two tool rounds; `/new`, then a reload inside the new conversation; reload; disable and a new process; binding timing while idle, then `/new` to show the save took effect; manual, repeated, post-reload and automatic compaction; built-in prompt off; a held tool turn whose continuation must keep revision 1 while a reload is attempted, then an ordinary turn at idle that must still carry revision 1 before the idle reload, so a reload wrongly committed while busy cannot hide behind the idle reload's no-op; the tools toggle and a model switch; a capability-less daemon). Cross-adapter X1–X3. Entry E1.

## The oracle

Every request is attributed to the step that caused it (the label set before the operation; a held turn's label stays active until its await completes). The expected request for each delivery comes from the frozen **pre-G1** request for the same step and the blueprint's composition rule, written out independently (§5; §6.3 A1): for a carrier, the first message is the base, `\n\n` when the base is non-empty, `User-configured instructions; revision <r>; selection <g>:\n` and the profile bytes, and the request carries `admission` version 1, optionally with a reserve within A2's bounds; for no carrier, the request equals its golden and carries no `admission`. The desktop base is the model-system text of the request's model; the terminal base is the golden's own leading system message, or nothing after `/system off`. Normalisation parameterises only the terminal prompt's date and both spellings of the sandbox path. No production composition code is called.

Captures are grouped by method as well as label and path. A model request sent to `/api/chat` or `/api/generate` with any method other than POST is scored as an incorrect delivery (`wrong-method`) or a failed preload, and is never frozen as a golden; any other request the fake refuses for its method is an auxiliary failure. Every JSON body is walked token by token, so each key and value is seen decoded and in order and numbers never fail the walk; a duplicate member anywhere in a request makes a scored delivery incorrect (`duplicate-member`), fails a checked summariser or preload, is an auxiliary failure on any other request, and is never frozen as a golden, because a decoder that keeps the last member reads a different request from the bytes on the wire. A JSON body that cannot be walked is an auxiliary failure.

Auxiliary traffic has its own expectations: a compaction summariser request only under a step that declares it, in exactly the declared number, equal to its frozen golden and carrying no header or profile text; a preload equal to its frozen golden; and no profile sentinel or carrier header anywhere else on any path. That last scan reads, for every capture, the decoded path, the raw request target, the query (raw, through the partial map `url.ParseQuery` returns even on error, and component by component, each key and value percent-decoded on its own), `Host`, headers and trailers; and the body of every capture not already compared with an expectation or a golden, through the token walk. Every one of those strings is scanned decoded, and a string that is itself a JSON document is walked in turn, so an escape cannot hide text. An inference path the ledger does not know makes the run invalid.

A terminal turn is complete when the daemon has fully written every response under its label **and the chat has proved it is idle**. The proof: with an empty input a single ctrl+d only arms quitting and sets a status (`cmd/tui/chat/chat.go` `updateCtrlD`, `armQuit`) that the chat draws only when no turn, compaction or approval prompt is active (`render.go` `renderActionStatusLines`, `notificationLine`); a run still in progress overwrites that status when it completes (`chatRunDoneMsg`), so the text cannot appear before the turn has ended. **The proof does not see a preload** (revision 3 claimed it did; the round-3 review showed otherwise): while a model preloads the chat draws no activity line (`render.go:1449`) and still draws notifications. So every step that starts a preload (a terminal start, the launcher's arrival in the chat, a model switch) first waits for the preload to finish at the daemon: the preload function (`cmd/agent_tui.go:583-608`) sends `POST /api/show`, `POST /api/generate` and then `GET /api/ps`, and returns once that last request is answered. Each probe clears the input first and ends with ctrl+u, which disarms the quit (`disarmQuit`). The daemon finishing and a quiet screen are not this proof: the chat's run can outlast both. Every wait is checked; a timeout is a harness failure. Before each typed line the driver sends ctrl+u, which clears the chat's input, so a command the chat kept as input while busy (`input.go:100`) cannot prefix a later line.

A terminal `/instructions` command reads "absent" on an unknown-command error and "no error seen" otherwise; the blueprint names no terminal output, so success and refusal are judged by the deliveries that follow (T8's held continuation and the ordinary turn after it for the refusal). T8's refused command must be handled while the turn is still held: after typing it the driver types a marker and waits until the chat's input box shows it, then clears it, before the await step releases the response. Keys are handled in order, so the marker proves the Enter reached the chat while no approval prompt could exist to take it. Saves pass only when the response (desktop) or exit status (CLI) agrees with the designated store's committed revision, enabled flag and text. Terminal identity is read from the store's event sequence: two conversations opened under distinct identities, and T2's reload recorded under the second.

Against a daemon without `chat.admission.v1` (T10), a terminal session may preload and go idle (the unchanged candidate does), or refuse at start-up: exiting, staying in an idle chat, or staying open elsewhere (at a picker, say), all of which A12 and §8 permit. A refusal is recognised only by its report: the daemon's version and a name for the refusal (`context_unavailable`, "context unavailable" or `chat.admission.v1`), compared case-insensitively with white space removed. A session that ends at start-up without that report is a harness failure, never a refusal; a banner that names the version before an unrelated failure does not pass. After a refusal the no-dispatch turn is typed only into an idle chat; otherwise the driver waits a declared five seconds for any request under the turn's step, and the stop step ends a session left open.

## Controls (run by `run.sh` before every measurement)

- **Scorer** (`TestOQ3ScorerControls`): expectations written by hand from the blueprint's words match the transform in all three shapes; a perfect delivery scores correct; twelve planted faults land in their categories and a multi-defect request counts once; a permitted reserve is accepted and four invalid admission objects are caught; both spellings of the sandbox path normalise; summariser faults are caught; the arithmetic reconciles; and T8 against a modelled adapter that commits a reload refused while busy: one bad delivery under this ledger, none under the round-2 ledger, none for a correct adapter.
- **Reference arm** (every run): the expected request for every scored delivery goes through real HTTP to a fresh fake daemon and must score correct. This shows HTTP and normalisation round-trip only; it cannot check the expectations themselves, which the hand-written scorer controls do.
- **Runner** (`TestOQ3RunnerControls`): empty and unknown selections refused; trial identities unique; a missing trial and a missing scenario caught; a malformed capture, an extra request and an unknown label invalidate the run; an undeclared summariser, instruction text in a metadata request, the same text JSON-escaped, in an object key, in JSON inside a string, in a header and in a query string, and a metadata request with a method the real daemon refuses are auxiliary failures, and a clean metadata request reports nothing; instruction text in a duplicate member (plain or escaped), behind a number too large for a float, in one query component beside a malformed one, as JSON inside a header value, in a trailer and in `Host` is reported, and a duplicate member without any instruction text is reported as a duplicate; an unknown inference endpoint invalidates the run; a desktop turn's own request replayed as PUT is refused 405 and scores `wrong-method`, the same body as POST scores correct, and the same body with a duplicate member, or with a carrier-bearing `messages` member ahead of the correct one, scores `duplicate-member`; a model switch whose preload is held back two seconds keeps its `/api/generate` under the switch; T8's refused command is handled while the turn is held, before any approval prompt appears in the transcript; on the real terminal, the idle probe reads an idle chat as idle and does not read as idle an open approval prompt after the daemon has answered every request (where daemon completion and a quiet screen both hold) or a held turn, and a command the chat kept as input while busy does not reach the next turn; a run whose turn is left waiting after the daemon finished is invalid at that turn; a start-up refusal that reports the missing capability is held and its turn scored as refused as required, whether the session exits or stays open outside a chat, and an exit at start-up without that report, or after a banner naming only the version, invalidates the run; a failing child invalidates it without changing the number.
- **Gate self-test** (`OQ3_GATE_SELFTEST=1`): `run.sh` blocks a failing test, a missing required test and an empty selection; the overlay is regenerated, checked and hashed before any test.
- **Repeat:** the baseline runs twice; the second compares against the goldens the first froze and must give identical per-trial verdicts.
- **Deliberate breaks** (revision 3, `../../proof_cont15/oq3-repair-r2/`; revision 4, `../../proof_cont15/oq3-repair-r3/`): each repair reverted alone in a scratch copy must make a control fail; a mutation expected to survive is declared, with its reason, before the run.

## Scope and known limits

`run.sh accept` is the **failure-number component** of G1-R-18's combined gate (§10): necessary, not sufficient. It does not replace I-09 (browser journey), I-10 (real models), I-13 (the daemon contract behind the capture point), the rest of I-14 (adapter behaviour for each daemon error), storage corruption, CAS, capacity and initialisation guards, production mutants and degenerate twins, the desktop's tool pass-loop continuation (needs an MCP server fixture; `startMCPManager` is in package `main`), the web-search family, tool-output-triggered compaction or `/new` failure injection. Fixture limits: one model family, short texts, no context pressure except the automatic-compaction trigger, serial schedules apart from the two held turns.

Instrument limits, stated so they are not mistaken for coverage. The terminal runtime's conversation ID (`m.chatID`, passed to `Session.Run` at `cmd/tui/chat/chat.go:1158`) is observable at no boundary the instrument reads: `api.ChatRequest` carries none, and the store's event sequence is written by the instruction bookkeeping, so the instrument cannot catch a `/new` that updates the binding but not the ID the runtime uses (gap 6). The leak scan decodes JSON and percent-encoding only; base64 and other encodings pass undecoded. The idle proof depends on the chat's quit prompt text and its status line, and the preload barrier on the preload function's order of requests; a change to any of them makes runs invalid (a harness failure), never a wrong number. The race T8's marker closes (an approval prompt taking the Enter) cannot be forced in a control; the control shows the marker reaching the chat before the approval prompt in the transcript. A refusal at start-up is recognised by the daemon's version and a name for the refusal, not by an exact text, which the blueprint does not give (gap 7): a correct report worded without any of those names would make the run invalid, not pass.

## Blueprint gaps this instrument exposed

1. The join between desktop model-system text and MCP instructions is unstated (`G1_PERSISTED_INSTRUCTIONS.md:204`); the oracle refuses to guess, so the fixture configures no MCP server. Open for OQ-4.
2. The terminal output of `/instructions reload|off` is unstated (§7). Handled by delivery evidence; still worth stating for the operator.
3. Whether `ollama instructions set` enables the profile: resolved in the blueprint (§7) in continuation 14 — `set` saves the file's text as an enabled profile.
4. The designated terminal instrument `cmd/tui/chat/instructions_test.go` sits below `GenerateAgentTUI`, where G1 creates the selection. Open for OQ-4: this instrument belongs in package `cmd`.
5. Whether a compaction summariser should carry the instructions is unstated; the instrument expects today's behaviour. Open for OQ-4.
6. The terminal runtime's conversation ID is observable nowhere (round-2 review, finding 2): §5's actual-request diagnostics record revision, generation, digest, byte count, model and outcome, not the conversation. Today's `/new` keeps the same ID (`resetChat`, `chat.go:997-1022`); G1 requires a new one bound before the old state is cleared (§4), and no boundary shows that the runtime uses it. Open for OQ-4: whether the diagnostics, or the request, carry the conversation ID. The empty-chat hint is a function of the ID (`chat.go:983-990`) but is cosmetic, collides by design and would tie the gate to interface text; it was considered and not used.
7. The terminal's report of a missing capability has no stated text (§7 and §8 say it names `context_unavailable` and the daemon's version, not what the operator reads). The instrument accepts the version with `context_unavailable`, "context unavailable" or `chat.admission.v1` (round-3 review, finding 3). Open for OQ-4: whether the report must carry the code verbatim.
