## Decisions

**Q1 — the number: (a), with its components and a separate validity verdict. Adopted in full.** Headline: (bad observed deliveries + missing required deliveries) / controlled conversation trials. Reported beside it: bad observed deliveries, missing required deliveries, observed deliveries, trials; per-category counts, stated to overlap; an observed request counts once in the numerator however many defects it has. Trial identities are frozen before execution and never dropped because a trial failed to start. A zero numerator is not acceptance: the run must also be complete and valid (Q5, Q7).

**Q2 — which requests are deliveries: (a), with an explicit request-purpose inventory. Adopted.** Each captured request is classified by the driver operation that caused it (the label set before the operation) and by structural marks unrelated to the carrier. User-turn requests, their retries and tool continuations are deliveries. The summariser's request has its own expectation: its system message is the compactor's own prompt and no carrier or profile sentinel appears in it; a failure blocks acceptance. Preload, show, status and other auxiliary traffic have their own expected shapes. An unclassified request makes the run incomplete.

**Q3 — the terminal boundary: Codex chose (a); decision changed to a layered design. Adopted.** The built `ollama` binary, driven in a pseudo-terminal through the launcher menu to the agent chat, is the entry-acceptance arm (E-scenarios). The detailed lifecycle scenarios run through (b): `launchInteractiveModel` in a re-executed test-binary process on a real pseudo-terminal, which is the exact function the launcher's run-model action calls (`cmd/cmd.go:2242`). It is described as the production launch function, not the complete CLI entry path. (c) is left to component diagnosis in the packs. The final instrument's location is an OQ-4 item: the designated `cmd/tui/chat/instructions_test.go` sits below `GenerateAgentTUI`, where G1 creates the selection, so it cannot carry the restart and new-conversation cases.

**Q4 — desktop restart: (a). Adopted** with verified termination: P1 is signalled, its exit is observed, and only then does P2 start. Omissions from the app's assembly (embedded daemon, MCP manager, updater, webview) are declared.

**Q5 — absent surfaces: (c), restricted to required delivery opportunities, with a predeclared event ledger. Adopted.** Every step is declared in advance as a required dispatch, a required refusal, a production operation with an expected outcome, or a harness action. Absent surfaces are attempted and their real responses recorded; later steps run anyway; no expectation is weakened because a save failed. Operation outcomes (save, reload, disable, CLI) have their own verdicts, independent of the delivery numerator. A harness failure (PTY, fake daemon, child start) makes the run invalid, never a delivery defect.

**Q6 — the oracle: (b), strengthened to the full composition contract. Adopted.** For an expected carrier: the first message has role `system` and is exactly the expected base, then (when the base is non-empty) the two-newline separator, then the header `User-configured instructions; revision <r>; selection <g>:` and a newline, then the profile bytes; no other message or field carries a header or profile sentinel; the conversation messages, tools, model, options, think and format equal their independent expectations; the request carries `admission` version 1. For no carrier: the request equals its frozen pre-feature golden (the variable date and paths parameterised) and carries no `admission` field. The desktop base is the model-system text from `/api/show`; the fixture configures no MCP server, because the blueprint does not state the separator between model-system text and MCP instructions (`G1_PERSISTED_INSTRUCTIONS.md:204`). That gap is recorded for OQ-4 and must be resolved before a combined-base golden is frozen.

**Q7 — controls: (a), (b), (d), (e) and a corrected (c). Adopted.** (a) scorer controls with independently authored cases, multi-defect requests, omissions, unexpected requests and arithmetic reconciliation; (b) a reference sender that composes correct requests by the blueprint's rules and sends them through the real HTTP client to the fake daemon, scored outside the candidate's numbers; (c) harness faults (malformed or truncated capture, misattribution, an omitted continuation, an extra request) must flip the integrity or cardinality verdict, not the delivery numerator; (d) runner controls: a failing child, a missing trial, an empty selection, a timeout, and discovery that reconciles started and finished trials; plus an unauthenticated request beside the authenticated control; (e) the baseline runs twice and its per-trial verdicts must match. Production mutants and degenerate twins belong to the final instrument; a red baseline earns no mutation credit.

**Q8 and Q9 — blind spots and false alarms. Adopted as the instrument's declared limits** (`../oq3-instrument/DESIGN.md`), each with its mitigation or its owner.

**Q10 — coverage. Adopted, split between this baseline and the final instrument.** In this baseline, attempted through the designated surfaces: binding timing (draft allocated before a save; terminal idle before its first prompt); a failed first desktop turn, its retry and a new identity; the genuine legacy transcript with continuation and explicit adoption; a held turn with a concurrent save and a refused reload, then reload at idle, on both adapters; cross-adapter persistence (desktop save to terminal, CLI save to desktop, terminal disable to desktop); disable, restore and reset in full, including A delivered before disabling and restart while disabled; compaction shown to have happened, with B saved before compacting A, repeated compaction, compaction after reload, and automatic compaction at the 80% threshold (`agent/compactor.go:144-154`, driven by the fake daemon's reported prompt count); two tool rounds on the terminal; model and tool switches (terminal `/tools off` and `on`, `/model` to a second fake model with different model-system text; desktop web search toggled on, which adds tools without calling them); terminal conversation identity read from the designated store's `conversations` table, a check that reports the surface absent until the store exists; and compatibility controls with `/system off` then `/system on`. Final instrument, owners the G1 packs, each with its reason: a real MCP server fixture and the desktop's MCP assembly for desktop tool continuations (the app's `startMCPManager` is in package `main` and cannot be reused, so this needs its own fixture), and the web-search family, whose execution reaches an external service; tool-output-triggered compaction (`agent/session.go:751`); `/new` failure injection, whose expected recovery depends on the store's failure surface; storage corruption, CAS, capacity and initialisation guards; I-09 to I-14; real-model qualification; production mutants and degenerate twins. Until then the desktop pass-loop continuation is unmeasured, and the report says so.
