**A-1: choose 3 — open the chat, announce the restriction, refuse submitted turns.**

This is principally a **product decision about recovery**. I favour keeping the operator inside the interface that provides `/instructions off`. The draft requires withholding carrier-bearing requests and reporting the cause; it does not require withholding the conversation itself. It also explicitly provides the disabling command ([G1_PERSISTED_INSTRUCTIONS.md:253](/Users/krypto/GitHub/ollama-eko-chat-read-integrity/docs/_design/G1_PERSISTED_INSTRUCTIONS.md:253), [G1:309](/Users/krypto/GitHub/ollama-eko-chat-read-integrity/docs/_design/G1_PERSISTED_INSTRUCTIONS.md:309)).

Specify one opening notice explaining that turns using saved instructions are blocked, then one fresh `error` entry for each refused submission. The existing terminal error path already leaves the chat open. Option 1 instead propagates through the launcher’s error-and-menu path ([chat.go:407–412](/Users/krypto/GitHub/ollama-eko-chat-read-integrity/cmd/tui/chat/chat.go:407), [cmd.go:2152–2156](/Users/krypto/GitHub/ollama-eko-chat-read-integrity/cmd/cmd.go:2152), [cmd.go:2180–2188](/Users/krypto/GitHub/ollama-eko-chat-read-integrity/cmd/cmd.go:2180)).

Keep the restriction at dispatch: use the capability result for the current connection, refresh it after reconnect, and permit ordinary dispatch after an explicit disabled selection commits. Carrier-free preload remains separate; its current request contains no prompt or carrier. A “slash commands only” state is less useful as a safety boundary because skill slash commands can themselves start runs ([G1:206](/Users/krypto/GitHub/ollama-eko-chat-read-integrity/docs/_design/G1_PERSISTED_INSTRUCTIONS.md:206), [G1:253](/Users/krypto/GitHub/ollama-eko-chat-read-integrity/docs/_design/G1_PERSISTED_INSTRUCTIONS.md:253), [agent_tui.go:598–608](/Users/krypto/GitHub/ollama-eko-chat-read-integrity/cmd/agent_tui.go:598), [chat.go:1098–1113](/Users/krypto/GitHub/ollama-eko-chat-read-integrity/cmd/tui/chat/chat.go:1098)).

**Would change my choice:** an explicit operator preference for rejecting incompatible sessions before opening, accompanied by an accessible launcher-level disabling action, would favour 1. **Risk:** opening a chat can imply readiness. The opening notice must make the restriction clear, and A-5 must make successful recovery equally clear.

**A-2: choose 2 — tokens within an attributable refusal entry.**

The existing version client returns that decoded string directly; the renderer already distinguishes error entries with an `err` marker ([api/client.go:454–464](/Users/krypto/GitHub/ollama-eko-chat-read-integrity/api/client.go:454), [render.go:487–488](/Users/krypto/GitHub/ollama-eko-chat-read-integrity/cmd/tui/chat/render.go:487)).

**A-5: choose 1 — named state values in slash output, typed codes in errors.**

The existing `/system` interaction provides the appropriate pattern: successful output uses slash entries, while invalid usage produces an error entry. A slash entry is already a distinct transcript role ([input.go:424–440](/Users/krypto/GitHub/ollama-eko-chat-read-integrity/cmd/tui/chat/input.go:424), [render.go:1816–1817](/Users/krypto/GitHub/ollama-eko-chat-read-integrity/cmd/tui/chat/render.go:1816)).

I would specify these outputs:

- `/instructions`: scope, selected revision, selection generation and selected enabled state. Show any saved-current revision separately so it cannot be mistaken for the active selection.
- `/instructions reload`: the committed resulting selection; explicitly identify an unchanged result when reloading the already-selected revision.
- `/instructions off`: the committed disabled revision and resulting selection, with the affected scope stated plainly.

That distinction follows the draft: continuing conversations retain their pinned selection; an idempotent reload retains its generation; `off` records and selects a disabled revision through the shared store ([G1:185–187](/Users/krypto/GitHub/ollama-eko-chat-read-integrity/docs/_design/G1_PERSISTED_INSTRUCTIONS.md:185), [G1:169](/Users/krypto/GitHub/ollama-eko-chat-read-integrity/docs/_design/G1_PERSISTED_INSTRUCTIONS.md:169), [G1:309](/Users/krypto/GitHub/ollama-eko-chat-read-integrity/docs/_design/G1_PERSISTED_INSTRUCTIONS.md:309)).

The draft requires errors to stop the affected change and preserve the old record; delivery-only evidence cannot establish what the operator was told ([G1:313](/Users/krypto/GitHub/ollama-eko-chat-read-integrity/docs/_design/G1_PERSISTED_INSTRUCTIONS.md:313), [DESIGN.md:37](/Users/krypto/GitHub/ollama-eko-chat-read-integrity/docs/analysis/colleague_integration/proof_cont14/oq3-instrument/DESIGN.md:37)).

**Would change my choice:** a persistent, tested instruction-status display could justify minimal success acknowledgements for `reload` and `off`; `/instructions` would still need its specified display. **Risk:** a convincing status message can describe the global profile while the conversation remains pinned elsewhere. Scope visibility is a product concern; named fields and entry roles are the engineering contract.

**A-6: choose 2 — make I-05 prove the identity used by the runtime.**

Observe the consumer, not just the newly allocated UUID: `m.chatID` supplies `RunOptions.ChatID`, which supplies event metadata ([chat.go:1157–1158](/Users/krypto/GitHub/ollama-eko-chat-read-integrity/cmd/tui/chat/chat.go:1157), [events.go:102–107](/Users/krypto/GitHub/ollama-eko-chat-read-integrity/agent/events.go:102)).

The acceptance path must include that entry, and the failure-number coverage statement must explicitly exclude this identity assertion.
