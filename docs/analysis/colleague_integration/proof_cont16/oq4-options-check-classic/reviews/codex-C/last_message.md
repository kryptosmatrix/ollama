**C-1 — Choose 2: the latest explicit `/set system` supplies the base.**

Use the model’s system text only when no session override exists. Compose once, during request construction, and omit the session’s `/set system` entries from the outgoing history. Preserve other messages, including model-provided `MESSAGE` history. Keep the composed carrier separate from `opts.System` and stored session messages: those are inputs to model creation through `/save` ([cmd/interactive.go:568](/Users/krypto/GitHub/ollama-eko-chat-read-integrity/cmd/interactive.go:568), [server/routes.go:2633](/Users/krypto/GitHub/ollama-eko-chat-read-integrity/server/routes.go:2633)).

This gives `/set system` a consistent override meaning, but **it is a product change, not literal preservation of today’s behaviour**. Currently, a later setting remains inside history; only a leading system message suppresses the model’s default. Option 2 removes that chronological distinction. Track whether an override was explicitly supplied separately from whether its text is empty ([cmd/interactive.go:369](/Users/krypto/GitHub/ollama-eko-chat-read-integrity/cmd/interactive.go:369), [cmd/interactive.go:389](/Users/krypto/GitHub/ollama-eko-chat-read-integrity/cmd/interactive.go:389), [server/routes.go:2634](/Users/krypto/GitHub/ollama-eko-chat-read-integrity/server/routes.go:2634)).

I prefer this to retaining superseded settings because A5 protects **every** system message from history fitting. Accumulated settings would therefore remain mandatory input. Preserve the existing construction when instructions are disabled, as G1 requires ([G1:246](/Users/krypto/GitHub/ollama-eko-chat-read-integrity/docs/_design/G1_PERSISTED_INSTRUCTIONS.md:246), [G1:79](/Users/krypto/GitHub/ollama-eko-chat-read-integrity/docs/_design/G1_PERSISTED_INSTRUCTIONS.md:79)).

**Would change my choice:** a requirement to preserve phased, historical system instructions. Then I would compose onto the existing leading base and retain later settings in position. **Risk:** option 2 changes the context in which earlier exchanges are presented; that semantic change needs explicit product wording.

**C-2 — Choose 2: `/clear` creates a conversation; `/load` retains the selection.**

Bind at session opening. `/clear` obtains a fresh identity and current selection before replacing the old state. `/load` clears the transcript but retains the pinned instruction selection, rebuilding the model-dependent base. This follows G1’s explicit distinction between a new conversation and a model change ([G1:183](/Users/krypto/GitHub/ollama-eko-chat-read-integrity/docs/_design/G1_PERSISTED_INSTRUCTIONS.md:183), [G1:189](/Users/krypto/GitHub/ollama-eko-chat-read-integrity/docs/_design/G1_PERSISTED_INSTRUCTIONS.md:189), [G1:191](/Users/krypto/GitHub/ollama-eko-chat-read-integrity/docs/_design/G1_PERSISTED_INSTRUCTIONS.md:191)).

Under C-1, retain an explicit session override across `/load`; use the newly loaded model’s default when there is no override. State this explicitly: current `/load` clears messages but does not clear `opts.System`, while `/clear` reintroduces that text ([cmd/interactive.go:223](/Users/krypto/GitHub/ollama-eko-chat-read-integrity/cmd/interactive.go:223), [cmd/cmd.go:1676](/Users/krypto/GitHub/ollama-eko-chat-read-integrity/cmd/cmd.go:1676), [cmd/interactive.go:279](/Users/krypto/GitHub/ollama-eko-chat-read-integrity/cmd/interactive.go:279)).

Add all three `/instructions` commands. Their plain-line output should name the selected revision, generation, enabled state, scope and separately the saved current revision. Reload and off must report committed outcomes or operation-specific codes. `/instructions off` must use the shared store’s disable-and-select transition, rather than merely removing prompt text ([OQ4 ADR:25](/Users/krypto/GitHub/ollama-eko-chat-read-integrity/docs/_design/ADR_2026-09-27_G1_OQ4_OPERATOR_CONTRACT.md:25), [G1:309](/Users/krypto/GitHub/ollama-eko-chat-read-integrity/docs/_design/G1_PERSISTED_INSTRUCTIONS.md:309)).

Exclude the injected carrier from classic `/save`. This command creates a model from session system text and messages; it is a different product operation from the agent chat’s request export. Exclusion should prevent embedding the injected carrier, without promising to redact instructions that ordinary transcript messages happen to quote ([cmd/interactive.go:267](/Users/krypto/GitHub/ollama-eko-chat-read-integrity/cmd/interactive.go:267), [cmd/interactive.go:568](/Users/krypto/GitHub/ollama-eko-chat-read-integrity/cmd/interactive.go:568), [OQ4 ADR:35](/Users/krypto/GitHub/ollama-eko-chat-read-integrity/docs/_design/ADR_2026-09-27_G1_OQ4_OPERATOR_CONTRACT.md:35)).

**This boundary is a product decision, and my confidence is lower here.** Both commands currently empty history; source alone cannot establish what “same conversation” should mean to the operator ([cmd/interactive.go:224](/Users/krypto/GitHub/ollama-eko-chat-read-integrity/cmd/interactive.go:224), [cmd/interactive.go:280](/Users/krypto/GitHub/ollama-eko-chat-read-integrity/cmd/interactive.go:280)). **Would change my choice:** an explicit expectation that `/load` means starting afresh, including adopting saved instructions; then choose 1. **Risk:** users may expect emptied history to imply a fresh selection. Show the retained revision after `/load`.

**C-3 — Choose 1, but say “no inference occurred”, not “nothing was sent”.**

A missing capability prevents dispatch. A daemon refusal can follow an HTTP request, while still preventing inference or cloud forwarding. Those are different observable outcomes ([G1:253](/Users/krypto/GitHub/ollama-eko-chat-read-integrity/docs/_design/G1_PERSISTED_INSTRUCTIONS.md:253), [G1:247](/Users/krypto/GitHub/ollama-eko-chat-read-integrity/docs/_design/G1_PERSISTED_INSTRUCTIONS.md:247), [G1:259](/Users/krypto/GitHub/ollama-eko-chat-read-integrity/docs/_design/G1_PERSISTED_INSTRUCTIONS.md:259)).

Print one error line immediately attributable to the submitted turn. Include the mapped code, the daemon version for capability failures, and whichever route, reason and counts the refusal supplies. Keep the command loop open. Stage the candidate turn separately, or restore the prior message state after a pre-inference refusal: current code appends the user message before calling `chat` ([cmd/interactive.go:527](/Users/krypto/GitHub/ollama-eko-chat-read-integrity/cmd/interactive.go:527), [G1:315](/Users/krypto/GitHub/ollama-eko-chat-read-integrity/docs/_design/G1_PERSISTED_INSTRUCTIONS.md:315)). Leave the submitted text visible and available for correction; excluding it from future model context need not erase what the user typed.

This couples directly to C-2: an open session provides access to `/instructions off`, reload and model changes. A startup notice is useful, but cannot replace the capability check and attributed refusal for each turn. Extend D-4’s separate mandatory refusal-report verdict to these classic-path cases ([OQ4 ADR:17](/Users/krypto/GitHub/ollama-eko-chat-read-integrity/docs/_design/ADR_2026-09-27_G1_OQ4_OPERATOR_CONTRACT.md:17), [OQ4 ADR:23](/Users/krypto/GitHub/ollama-eko-chat-read-integrity/docs/_design/ADR_2026-09-27_G1_OQ4_OPERATOR_CONTRACT.md:23)).

**Product decision:** whether recoverable admission failures close an interactive session and whether refused input enters future context. **Would change my choice:** an operator requirement for immediate termination, together with a usable disable mechanism outside that session. **Risk:** the prompt can appear ready while every turn will be refused; the opening notice and recovery command must make that state explicit.

**C-4 — Choose 1: extend `/api/generate`, using its `system` field.**

Send `System = Compose(modelSystem, selection)` and leave the operator’s prompt in `Prompt`. The generate handler already treats non-empty `System` as the override and constructs system text, model messages and the user prompt before entering the shared native or Go-rendered fitting paths ([G1:200](/Users/krypto/GitHub/ollama-eko-chat-read-integrity/docs/_design/G1_PERSISTED_INSTRUCTIONS.md:200), [server/routes.go:520](/Users/krypto/GitHub/ollama-eko-chat-read-integrity/server/routes.go:520), [server/routes.go:561](/Users/krypto/GitHub/ollama-eko-chat-read-integrity/server/routes.go:561), [server/routes.go:604](/Users/krypto/GitHub/ollama-eko-chat-read-integrity/server/routes.go:604)).

Option 2 contradicts D-11’s explicit extension to generate. It also changes message ordering: chat prepends model messages before request messages, whereas generate places its system message before model messages. Option 3 changes the carrier’s role and contradicts the specified system composition ([OQ4 ADR:37](/Users/krypto/GitHub/ollama-eko-chat-read-integrity/docs/_design/ADR_2026-09-27_G1_OQ4_OPERATOR_CONTRACT.md:37), [server/routes.go:2633](/Users/krypto/GitHub/ollama-eko-chat-read-integrity/server/routes.go:2633), [G1:204](/Users/krypto/GitHub/ollama-eko-chat-read-integrity/docs/_design/G1_PERSISTED_INSTRUCTIONS.md:204)).

**C-5 — Choose 2: separate route capabilities, one shared contract definition.**

Use `chat.admission.v1` for chat and `generate.admission.v1` for generate. Read the applicable capability before every carrier-bearing request, obtaining the version from that same response. A route capability should promise enforcement and the specified refusals; it should not promise support for every model or request form ([G1:251](/Users/krypto/GitHub/ollama-eko-chat-read-integrity/docs/_design/G1_PERSISTED_INSTRUCTIONS.md:251), [G1:253](/Users/krypto/GitHub/ollama-eko-chat-read-integrity/docs/_design/G1_PERSISTED_INSTRUCTIONS.md:253), [OQ4 ADR:17](/Users/krypto/GitHub/ollama-eko-chat-read-integrity/docs/_design/ADR_2026-09-27_G1_OQ4_OPERATOR_CONTRACT.md:17)).

This lets each adapter state its actual requirement and permits independent route qualification. A renamed aggregate capability unnecessarily couples availability; widening the chat-named capability obscures its scope. This is protocol engineering, rather than a new instruction-selection policy.

**Would change my choice:** a deliberate commitment to implement, qualify and release both routes as an indivisible unit; option 1 would then be reasonable. **Risk:** independently advertised routes can drift semantically, so they should share admission definitions and conformance cases. Also, [Inference] a capability read cannot eliminate daemon replacement between the read and dispatch; the mandatory final report detects a contract failure but cannot undo an already transmitted carrier ([OQ4 ADR:17](/Users/krypto/GitHub/ollama-eko-chat-read-integrity/docs/_design/ADR_2026-09-27_G1_OQ4_OPERATOR_CONTRACT.md:17)).

**C-6 — Choose 2: an immutable selection for one invocation, without a conversation binding.**

Read and validate the current profile once, retain an independently owned snapshot through the invocation, and compose every request belonging to that invocation from that snapshot. A concurrent save must not change it. This uses the same validation and immutability principles as bound selections, without claiming a binding was committed ([G1:115](/Users/krypto/GitHub/ollama-eko-chat-read-integrity/docs/_design/G1_PERSISTED_INSTRUCTIONS.md:115), [G1:163](/Users/krypto/GitHub/ollama-eko-chat-read-integrity/docs/_design/G1_PERSISTED_INSTRUCTIONS.md:163)).

I would reserve **generation `"0"`** for an explicitly typed one-shot selection, yielding `selection 0` in the carrier header. Bound selections continue to start at 1. This requires amending the selection vocabulary and composer contract; it must not be an ordinary binding with an invented generation. No binding, `opened` event, reload transition or conversation lease is claimed ([G1:104](/Users/krypto/GitHub/ollama-eko-chat-read-integrity/docs/_design/G1_PERSISTED_INSTRUCTIONS.md:104), [G1:167](/Users/krypto/GitHub/ollama-eko-chat-read-integrity/docs/_design/G1_PERSISTED_INSTRUCTIONS.md:167), [G1:200](/Users/krypto/GitHub/ollama-eko-chat-read-integrity/docs/_design/G1_PERSISTED_INSTRUCTIONS.md:200)).

Option 1 consumes the finite shared binding allowance for unrelated batch invocations. Option 3 puts independent invocations behind one conversation lease and eventually encounters the reload cap as revisions change. Option 4 merely moves the unresolved capacity decision into a new retention policy ([G1:119](/Users/krypto/GitHub/ollama-eko-chat-read-integrity/docs/_design/G1_PERSISTED_INSTRUCTIONS.md:119), [G1:169](/Users/krypto/GitHub/ollama-eko-chat-read-integrity/docs/_design/G1_PERSISTED_INSTRUCTIONS.md:169), [G1:179](/Users/krypto/GitHub/ollama-eko-chat-read-integrity/docs/_design/G1_PERSISTED_INSTRUCTIONS.md:179)).

**This is a product decision:** whether every invocation acquires durable selection history and competes with interactive conversations for capacity. D-11 settles coverage, not that retention promise ([OQ4 ADR:37](/Users/krypto/GitHub/ollama-eko-chat-read-integrity/docs/_design/ADR_2026-09-27_G1_OQ4_OPERATOR_CONTRACT.md:37)). **Would change my choice:** a requirement to recover each invocation’s selected revision from durable records; then choose per-run bindings with an explicitly adequate capacity/retention policy. **Risk:** the instruction store cannot subsequently prove which revision a particular one-shot run selected. Revision and digest diagnostics remain useful, but are not a substitute for an `opened` record ([G1:208](/Users/krypto/GitHub/ollama-eko-chat-read-integrity/docs/_design/G1_PERSISTED_INSTRUCTIONS.md:208)).

**For one-shot output, put all new admission diagnostics on stderr.**

Keep stdout’s existing response stream unchanged; it currently receives generated text directly. Inspect the final admission record even when that record contains no visible response text ([cmd/cmd.go:1921](/Users/krypto/GitHub/ollama-eko-chat-read-integrity/cmd/cmd.go:1921), [cmd/cmd.go:1949](/Users/krypto/GitHub/ollama-eko-chat-read-integrity/cmd/cmd.go:1949), [G1:250](/Users/krypto/GitHub/ollama-eko-chat-read-integrity/docs/_design/G1_PERSISTED_INSTRUCTIONS.md:250)).

- **Local context exhaustion:** one stderr notice naming `context_exhausted`, context length and reserve. Do not derive it from `done_reason: length`, which also covers an output-budget stop ([G1:250](/Users/krypto/GitHub/ollama-eko-chat-read-integrity/docs/_design/G1_PERSISTED_INSTRUCTIONS.md:250)).
- **Cloud threshold:** at `prompt_bound >= 80% × limit`, print the model, bound, verified limit and remaining bound allowance. Call it verified prompt allowance, not available model context; the daemon does not observe the latter ([G1:261](/Users/krypto/GitHub/ollama-eko-chat-read-integrity/docs/_design/G1_PERSISTED_INSTRUCTIONS.md:261), [G1:307](/Users/krypto/GitHub/ollama-eko-chat-read-integrity/docs/_design/G1_PERSISTED_INSTRUCTIONS.md:307)).
- **Admission refusal:** return one error containing the code and available version/route/counts, with exit status 1. The existing `main` error path already prints to stderr and exits 1 ([main.go:12](/Users/krypto/GitHub/ollama-eko-chat-read-integrity/main.go:12), [cobra.go:227](/Users/krypto/go/pkg/mod/github.com/spf13/cobra@v1.7.0/cobra.go:227)).

Previously streamed stdout cannot be recalled; explicitly describe the result as unverified, rather than claiming that inference was refused before it began ([OQ4 ADR:17](/Users/krypto/GitHub/ollama-eko-chat-read-integrity/docs/_design/ADR_2026-09-27_G1_OQ4_OPERATOR_CONTRACT.md:17), [cmd/cmd.go:1949](/Users/krypto/GitHub/ollama-eko-chat-read-integrity/cmd/cmd.go:1949)).
