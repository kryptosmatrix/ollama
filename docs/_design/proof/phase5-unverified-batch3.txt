Phase 5 — working down the unverified list, batch 3

Two confirmed and fixed, one refuted and kept as a standing test.

C-3 — CONCURRENT SAVES LOST TOKENS, AND FAR MORE THAN EXPECTED

Save and Delete read the whole file, change one entry and write it back. The
review said two interleaved saves for different servers could lose one. The
measurement was worse:

    CONFIRMED C-3: 1 of 8 tokens survived concurrent saves: [two]

Eight goroutines saving eight different servers left one token on disk. Every
other sign-in was silently destroyed.

Serialised now, keyed by resolved path in a package-level map rather than held
on the store — several places build a fresh FileTokenStore for the same file,
and a lock on one of those values would not see another.

WHAT THIS DOES NOT FIX, and the store's own comment says so: the window between
*processes*. The desktop app and a terminal saving at the same instant can still
lose one. Closing that needs a lock file, which brings staleness after a crash
and a steal-timeout to go with it — a design decision rather than a patch, and
not one to make at the tail of a long session. Recorded as owed.

B-5 — THE TOKEN SOURCE'S LAST-WRITTEN VALUE WAS UNGUARDED

Confirmed by the race detector. A token source is consulted from whatever
goroutine is making a request; this one remembers the last access token it wrote
so it does not rewrite the store on every call, and that field was read and
written with no lock. Guarded now.

D-5 — REFUTED

The review expected a stdio subprocess that starts and then fails the MCP
handshake to survive until the manager closes, since the stdio release function
is a no-op. It does not: the protocol library kills it.

    status after a failed handshake: failed (connect: connection closed:
    calling "initialize": invalid character 'o' in literal null)
    --- PASS: TestProbeD5StdioLeak

This is the same guarantee that led to deleting a per-server reaping mechanism
in Phase 2, after three separate attempts to falsify it all passed. It now
carries a standing test — TestAStdioServerThatFailsItsHandshakeIsNotLeft —
because the next reader will have exactly the same suspicion, and a refutation
that leaves no trace gets re-litigated.
