Phase 5 — working down the unverified list, batch 4

Four more settled: three confirmed and fixed, one real but with no production
consumer, fixed anyway because it was four lines.

E-3 — additionalProperties GIVEN AS A SCHEMA WAS DROPPED IN SILENCE

Only the literal false was reported. A server saying "anything extra must look
like this" had its constraint discarded, and silence in that position reads to
the model as "anything extra is fine" — the opposite of what the server said.
All three cases are now distinguished: false is reported, a schema is reported
as unrepresentable, and true says nothing because it constrains nothing.

E-5 — TWO HEADER NAMES SHARED ONE ENVIRONMENT VARIABLE

    headers: map[X-Custom-Auth:${env:X_CUSTOM_AUTH}
              X_Custom_Auth:${env:X_CUSTOM_AUTH}]

Both reduce to X_CUSTOM_AUTH, so the user sets one value and both headers
receive it. If they were meant to carry different credentials, one of them is
silently wrong. Each name now gets its own reference, and the second becomes
X_CUSTOM_AUTH_2.

A2-2 — THE CANNOT-COMPUTE MARKER WAS A COLLISION CLASS

Fingerprint returns a constant when a spec cannot be marshalled, and the comment
beside it claimed the value matched nothing. It matched every other spec that
also failed to marshal. The review called this unreachable with the current
struct; it is not. An unknown field preserved from the configuration file is
carried as raw JSON, and raw JSON that cannot be re-marshalled makes the whole
spec unmarshalable — which is how the test reaches it.

Approve now refuses to store the marker and Allows refuses to accept it.

THE SECOND GUARD LOOKED REDUNDANT AND IS NOT. With Approve refusing to store,
Allows can never meet the marker in a ledger this build wrote, and the first
sabotage of the Allows guard passed for exactly that reason. But earlier commits
*on this branch* did store it, so a ledger written by one of them contains the
marker — and reading one back must not admit anything either. The test now
covers that, and the sabotage fails. A guard that is unreachable today can be
reachable in a file written yesterday.

C-2 — Servers() MISSED A SERVER STILL IN THE FALLBACK

Real, and with no production caller today: Servers() is not part of the
TokenStore interface. Fixed anyway because it is four lines, and a list of
sign-ins that omits one is the kind of thing a future surface would trust.

FALSIFICATION

X3 appears three times. The first run passed because the test used a spec that
marshals cleanly, so the marker was never reached. The second passed because
Approve's guard already prevented the ledger from holding the marker. Only the
third — against a ledger of the kind an older build wrote — discriminates. Both
earlier runs are kept, because a falsifier that passes is a statement about the
test, and this one took two attempts to become a statement about the code.
