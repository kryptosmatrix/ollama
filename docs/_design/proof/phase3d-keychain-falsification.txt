Phase 3d — the macOS keychain token store
Falsification record

Eleven protections, each broken in mcp/tokenstore_darwin.go, observed to fail
its test, and restored byte-identical. Hash before and after every attempt:
1458d4bd8cb6a7be228523d649a1d4c236f02925e12018f7dd370e62310d11af

THESE TESTS USE THE REAL LOGIN KEYCHAIN. A keychain that is stood in for proves
nothing about the keychain, so they write to the actual one — scoped to a
service name carrying the test's own name, cleared before the test as well as
after, and never touching the "Ollama MCP" service a real sign-in uses. The
record ends with a count of leftover items, which is zero.

WHAT THE MEASUREMENT SHOWED, and why the description is worded as it is. Before
writing any of this, a spike wrote a keychain item from one unsigned binary and
read it back from a *different* unsigned binary. It succeeded with no prompt.
So on this platform an item added by an unsigned build is readable by any
process running as the same user. The honest claim is therefore encryption at
rest — the token stops sitting in cleartext in a file that gets swept into
backups, sync folders and support bundles — and not isolation from other
programs. K9 breaks the description into the overclaiming version and the test
fails, which is the only way that wording stays honest as the code changes.

A DEFECT THE PASS ITSELF CAUSED, recorded rather than tidied away. K10 removes
the account from the item query. Under that sabotage the store created items
with no account, and the test's own cleanup — which listed servers through the
same broken query — could no longer find them. Two items were left in the real
login keychain and had to be removed by hand. The cleanup now sweeps by service
name through `security delete-generic-password`, which shares no code with the
store under test. That tool is refused for *storing* a token because the secret
would appear in the process list; deleting by service name passes no secret, so
the objection does not apply. K10 was then re-run and left nothing behind.

Not built, and not written as unproven code: the Windows DPAPI store and a
Linux secret-service store. Both are owed. Neither can be run on this machine,
and code that compiles but has never executed is exactly what "full or stop"
forbids — so DefaultTokenStore on those platforms returns the file store, whose
Description says plainly what protects it, and every surface shows that string
before a token exists.

Re-run of every keychain falsifier after the C helpers replaced the
unsafe.Pointer conversions, so the record matches the committed file.
