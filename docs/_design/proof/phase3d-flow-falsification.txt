Phase 3d — the complete authorization-code flow
Falsification record

The tests this file covers live in mcp/oauthflow_test.go and run against
authorizedMCPServer: a hosted MCP server that refuses an unauthenticated
request, together with the authorization server that issues one. It implements
enough of RFC 9728, RFC 8414, RFC 7591, RFC 7636 and RFC 7009 to drive Ollama's
own sign-in from end to end — 401 with a challenge, resource metadata,
authorization-server metadata, dynamic client registration, an authorize
endpoint that redirects, a token endpoint that verifies the PKCE verifier
against the committed challenge, refresh, and revocation. The browser is stood
in for by a function that follows the redirect, which is how the authorization
code lands on Ollama's own loopback listener exactly as a real browser would.

That last detail matters: the fake user is *already signed in* and is redirected
back immediately. A listener bound after the browser was opened would lose the
callback, and this is the arrangement that catches it.

Method: each protection was broken in production code, the test that exists to
catch it was observed to fail, and the file was restored byte-identical. Each
file had its own backup path this time.

Two defects were found by writing these tests, before any sabotage:

  1. AN ORDINARY CONNECTION REGISTERED A CLIENT AT THE SERVICE. The protocol
     library's authorization flow performs discovery and dynamic client
     registration *before* it asks whether a browser may be opened, so
     refusing at the fetcher — which is what the whole signInDisallowed design
     rested on — happened too late. Every launch and every reconnect of a
     remote server the user had not signed in to announced this installation
     to the authorization server and left a client registration behind. The
     test that found it asserts zero registrations on the ordinary path; it
     failed with two.

     The fix is signInRequiredTransport: in every mode but an explicit
     sign-in, a 401 carrying a Bearer challenge becomes ErrSignInRequired at
     the RoundTripper, so the library never reaches its authorization branch.
     A handler is now attached only when there is a stored token to send.
     The ordinary path touches the MCP endpoint and nothing else.

  2. A REDUNDANT SECOND WRITER FOR THE STORED TOKEN. savingTokenSource wrote
     the freshly exchanged token, and persistingTokenSource wrote it again on
     first use. Two attempts to falsify the first write both passed, including
     one against a test built specially to discriminate — a sign-in that
     completes and *then* fails to connect, where the token must survive. The
     transport consults the token source immediately after the exchange, so
     there is no path where the second writer has not already run. The first
     was deleted, on the same rule that removed the per-server reaping code in
     Phase 2: code that looks like a safety measure and cannot be tested
     misleads its next reader. The remaining single writer is falsified below
     by four independent tests.

Two more protections had no discriminating test and got one written rather than
a claim softened: a sign-in must end when the caller gives up rather than run
to its own timeout (TestSignInStopsWhenTheCallerGivesUp), and a token must
survive a connection that fails after the exchange.

NOT FALSIFIABLE AGAINST OUR CODE, and recorded rather than counted: the PKCE
assertions. TestTheWholeSignInFlow checks that the authorization request
carried code_challenge_method=S256 and a challenge, that the token request
carried a verifier, and that the verifier hashes to the challenge — and the
fake server refuses the exchange otherwise. But PKCE is generated inside the
protocol library, and there is no line of Ollama's that can be broken to make
those assertions fail. They guard against an SDK regression or a future
hand-rolled flow, which is worth having; they are not a protection of ours and
are not claimed as one.
