Phase 3d — against real hosted MCP servers
Activation evidence

Everything else in mcp/ runs against a server this repository controls. That is
what makes those tests deterministic, and it is also their ceiling: a server
written to satisfy this client agrees with whatever this client does. These runs
are against services that have never heard of Ollama.

The harness is mcp/hosted_test.go. It is skipped unless OLLAMA_MCP_TEST_URL
names an endpoint, so the committed suite never depends on somebody else's
uptime, and it uses a token store in a temporary directory rather than the
platform default, so nothing a run obtains lands beside a real sign-in.

WHAT THESE RUNS PROVE

1. A real hosted MCP server connects, over real TLS and a real streamable HTTP
   session, and its tools convert. DeepWiki 2.14.3 speaking protocol
   2025-11-25, three tools offered and none refused, schemas converted and
   marshalled. This is the first time the transport and the schema conversion
   have met a tool list nobody here designed.

2. A real tool call round-trips. read_wiki_structure against ollama/ollama
   returned 1747 bytes of content with isError=false.

3. Three real OAuth-protected services report a needed sign-in rather than
   failing obscurely: Linear, Sentry and Notion. Each returns
   ErrSignInRequired, wrapped through the transport and recovered by
   errors.Is at the manager — which is the part that could not be proven by
   reasoning, because the error crosses the protocol library's own wrapping on
   the way.

WHAT THESE RUNS DO NOT PROVE, and why the record says so rather than implying
otherwise.

  a. No complete sign-in has been performed against a real service. Discovery,
     registration, PKCE, the exchange and refresh are proven against the fake
     authorization server in mcp/oauthflow_test.go. What is unproven is
     whatever real services do differently: consent screens needing more than
     one round trip, scope names, an authorization server on a different host
     from the MCP endpoint. TestAHostedSignIn exists and is skipped; running it
     needs an operator with an account, at a keyboard, and their decision.

  b. The zero-registration property is NOT directly observed here. Against the
     fake server it is asserted exactly — an ordinary connection produces no
     registrations and no authorization requests. Against a real service it
     cannot be observed from outside, and proving it by removing
     signInRequiredTransport would create a junk client registration at a
     third party's authorization server, which is not a thing to do to
     somebody else's service to make a point. The indirect signal is in the
     timings below: 0.05s, 0.07s and 0.07s. Discovery followed by dynamic
     client registration is several round trips to two hosts and cannot happen
     in that time. Recorded as an indication, not as a measurement.

WHAT WAS CONTACTED, so the network these runs used is on the record:
mcp.deepwiki.com, mcp.linear.app, mcp.sentry.dev and mcp.notion.com. Every
request was anonymous; no credential was sent to any of them and none was
obtained. The DeepWiki tool call is a read of public documentation.
