The four that carry the most weight:

  S1  Sign-out that only deletes the token locally. This is the default
      mistake — it is one line shorter and looks finished — and it leaves a
      valid credential at the service that the user believes they withdrew.
  S4  A token that could not be revoked being left on the machine. Failing to
      revoke is not a reason to keep using it.
  S5  A failed revocation reported as a clean sign-out. The user is told,
      because the remedy is theirs: withdraw Ollama's access in the service's
      own account settings.
  S9  An explicit sign-in connecting with signInDisallowed, which would mean
      no path in the program could ever open a browser and OAuth could never
      complete. The mirror of F1 in the handler's own record: one test proves
      the ordinary path cannot sign in, this one proves the explicit path can.

The revocation tests run against a fake authorization server built in
signin_test.go, which serves RFC 9728 resource metadata and RFC 8414
authorization-server metadata and records every revocation request. Asserting
what reached that endpoint — the refresh token in preference to the access
token, the type hint, the client identifier — is the only way to tell a real
revocation from a local delete wearing its name.
