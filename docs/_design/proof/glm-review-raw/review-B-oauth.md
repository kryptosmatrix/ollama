## Findings

### HIGH — OAuth error callback loses the error reason

**File:** `mcp/oauth.go`, line 184

The error branch of `handleCallback` calls `r.deliver(sdkauth.AuthorizationResult{State: query.Get("state")})` directly instead of `r.deliverFailure(detail)`. `deliver` sends a result with an empty `Code` but never sets `r.failure`. In `Fetch` (lines 144–152), an empty `Code` causes it to read `r.failure`; since that is still empty, the user gets the generic message `"the sign-in was not completed"` rather than the `error`/`error_description` the authorization server returned. Compare with the issuer-mismatch path at line 202, which correctly calls `deliverFailure`. A user whose sign-in is refused by the server (e.g. `access_denied`, `invalid_scope`) sees a useless generic error and cannot diagnose the problem.

### HIGH — `ExpectedIssuer` and `IgnoreIssuer` are never set; RFC 9207 check and the unadvertised-iss workaround are both dead

**File:** `mcp/oauthhandler.go` (lines 96–107), `mcp/oauth.go` (lines 199–207)

`newOAuthSession` creates the `LoopbackRedirect` and never assigns `ExpectedIssuer` or `IgnoreIssuer`. The `issuerExpectation` function (`mcp/oauthhandler.go` line 213) that is supposed to supply these values is defined but never called anywhere in the shown code. Both fields remain at their zero values (`""` and `false`).

Consequences:
1. The issuer comparison at `oauth.go:200` — `if issuer != "" && r.ExpectedIssuer != "" && …` — is short-circuited because `r.ExpectedIssuer` is always `""`. The mix-up attack defence the code claims to implement never runs.
2. `IgnoreIssuer` is `false`, so `iss` is always passed through to the protocol library. The comments at lines 56–65 explain that the library treats an unadvertised `iss` as fatal and refuses the sign-in, and that `IgnoreIssuer` exists to strip it for servers (like Sentry) that send `iss` without advertising it. With `IgnoreIssuer` never set, a user trying to sign in to such a server gets a hard failure every time.

### MEDIUM — Revocation may target the wrong authorization server

**File:** `mcp/signin.go`, lines 198–206

`revocationEndpoint` iterates `metadata.AuthorizationServers` and returns the first server that has a `RevocationEndpoint`. The `SignInRecord` stores only `Token` and `ClientID`, not which authorization server issued the token. If the MCP resource advertises multiple authorization servers, the revocation request is sent to the first one with a revocation endpoint, which may not be the one that issued the token. Per RFC 7009 §2.2 the wrong server returns 200 for an unrecognized token, so `revokeSignIn` reports success, the local token is deleted, and the user is told they are signed out — but the token remains valid at the issuing server. This violates the requirement that "signing out must actually revoke at the authorization server."

### MEDIUM — Revocation request can leak the token over plain HTTP

**File:** `mcp/signin.go`, lines 163–169

`revokeSignIn` constructs the request with `http.NewRequestWithContext(ctx, http.MethodPost, endpoint, …)` where `endpoint` comes directly from the authorization server's metadata (`server.RevocationEndpoint`). No check enforces HTTPS. If the metadata publishes an `http://` revocation endpoint (or a network attacker can tamper with the metadata when the MCP server itself is reached over HTTP), the refresh or access token is sent in cleartext over the network. A network attacker who can read the traffic obtains a live token.

### LOW — `persistingTokenSource.last` is accessed without synchronization

**File:** `mcp/oauthhandler.go`, lines 184–189

`persistingTokenSource.Token()` reads and writes `p.last` without a lock. If the underlying token source is consulted concurrently (the `oauth2` transport can do this on parallel requests), two goroutines can both observe `token.AccessToken != p.last`, both call `p.store.Save`, and both update `p.last`. The consequence is a redundant disk write, not data corruption, so the impact is limited.

### No defect found

- **Browser opened by a background reconnect:** The `signInMode` / `refuseSignIn` design correctly ensures only `signInAllowed` connections can open a browser, and `refuseSignIn` returns `ErrSignInRequired` without calling `Open`.
- **Cross-flow callback aborting a sign-in:** The `state` check in `handleCallback` correctly rejects callbacks whose state does not match, and a rejected callback does not end the wait.
- **Authorization code obtainable by another local process:** The loopback listener binds to a random port and the `state` parameter (generated by the SDK) is required; a local process cannot craft an accepted callback without knowing the state.
