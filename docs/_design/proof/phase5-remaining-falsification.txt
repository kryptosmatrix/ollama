Phase 5 repairs — the last three confirmed findings

All three now carry a test that fails without the change. Five protections
falsified; hashes before and after every attempt are in this file and match.

B-1 — A REFUSED SIGN-IN LOST THE SERVER'S REASON

The error branch of handleCallback delivered an empty result rather than a
failure with a reason, so Fetch fell back to the generic "the sign-in was not
completed" and the authorization server's own error and error_description —
access_denied, invalid_scope, a message naming a permission an administrator has
not granted — were shown on the browser page and thrown away. That message is
the only place a user can learn why they were refused.

It now goes through deliverFailure, and the reason is sanitised and bounded on
the way: it is a third party's text arriving in something a person reads.

A PRE-EXISTING TEST HAD TO GO, and it is worth being explicit about why.
TestARefusedSignInIsReported asserted that the error contained "not completed" —
that is, it asserted the defective behaviour. It was written when the generic
message was all there was, and it would have failed this repair. A test can
encode a bug as firmly as the code does. It is superseded by
TestARefusedSignInSaysWhy, which asserts everything it did and the reason as
well; deleting it was a decision, not housekeeping, and this paragraph is here
so that nobody has to guess which.

C-1 — A FAILED MIGRATION LEFT THE CREDENTIAL IN CLEARTEXT FOR EVER

Load saved the token into the keychain and then deleted the file copy. If the
save succeeded and the delete failed, the token existed in both places, and
every later Load found the keychain item first and returned — so the cleartext
copy was never retried and never removed. It also returned the delete error,
which meant a perfectly usable token failed to load at all.

Both halves are wrong and both are fixed. The cleanup is retried on the
keychain-hit path, so the condition heals as soon as whatever blocked it clears,
and a cleanup that cannot run no longer signs the user out of a server whose
token works. R4 and R5 are the two falsifiers, one for each half.

E-2 — A PACKAGE IDENTIFIER WAS NEVER CHECKED FOR BEING A FLAG

The registry-supplied identifier went straight into the runner's argument list.
An entry naming itself "--call=..." produces a command line npx reads as an
instruction rather than a package. Refused now, for all three ecosystems, along
with a version that begins with a dash.

The approval gate always stood in front of this — the user is shown the exact
command line — but "the user will read it" is the mitigation this codebase
refuses to rely on everywhere else, and a resolver whose contract is that a
command line is derived rather than guessed must not derive one from a value it
never checked. Refusing costs a publisher nothing they can legitimately want: a
package name never begins with a dash.

WHAT THIS DOES NOT COVER, and it is the same asymmetry as the query-string case

Docker runtime arguments are publisher-supplied flags by design —
"docker run --rm -i <publisher's flags> <image>" — so a registry entry can
inject "-v /:/host". A blanket refusal would break legitimate entries that need
an environment variable or a volume, which is exactly the shape of decision I
declined to make alone for query-string credentials. The control there remains
the approval gate showing the whole command line verbatim. Recorded for the
operator rather than fixed quietly or ignored.
