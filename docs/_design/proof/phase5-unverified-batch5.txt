Phase 5 — working down the unverified list, batch 5

Two confirmed and fixed. Three left standing, with reasons.

A1-2 — A CREDENTIAL IN A PRESERVED FIELD WENT STRAIGHT THROUGH

Fields this version of Ollama does not understand are kept and written back,
which is what keeps a configuration portable between MCP clients. It is also how
a credential arrives in one: the env and header checks never saw a name like
"apiKey" sitting directly on the server object.

    CONFIRMED A1-2: an unknown field carried a credential straight through

Refused now, by the same name pattern the env check already uses, and the
refusal names the safe form. An unknown field that is not credential-shaped is
still preserved — that is the whole point of keeping them — and an environment
reference in such a field is left alone, because a newer Ollama might read it.

E-6 — A HOSTILE DESCRIPTION WAS COPIED TWICE AT FULL SIZE

sanitiseText walked every rune of its input, built the whole sanitised string,
and then made a second full copy as runes to keep the first four thousand. Tool
descriptions arrive from an MCP server with no length agreed anywhere. It now
cuts to a generous multiple of the cap before doing any work; the test sanitises
an eight-megabyte description and asserts the allocation stays under two
megabytes.

WHAT IS LEFT, AND WHY IT IS LEFT

A1-3 — Args are neither checked for credentials nor expandable from the
environment. This is a judgement, not an oversight, and it is the same shape as
the query-string and docker-runtime-argument cases already put to the operator.
The threat model names the process argument list explicitly, so the right answer
looks like refusing a credential there — but the pattern that would catch
"--api-key=sk-..." also catches "--token-file=/etc/foo", where the value is a
path and refusing it strands the user with no alternative, since expanding
${env:NAME} into argv would put the secret in the process list, which is the
thing being avoided. Three cases now share this shape; they should be ruled on
together rather than one at a time.

B-3 — Revocation goes to the first authorization server advertising a
revocation endpoint, and the record does not say which one issued the token. The
fix is to store the issuer at sign-in beside the client identifier, which is
another field on SignInRecord threaded through the same places ClientID goes.
That is a clean change and a wrong one to make at the tail of a long session:
the last credential-store reshape needed care over migration and a refresh that
arrives carrying nothing. It is specified here rather than half-done.

D-4 — dial closes the previous session while holding the write lock, where
closeSession deliberately does the same work outside it. Real, and a liveness
issue rather than a correctness one. A discriminating test needs a session whose
Close blocks; the transport seam controls the release function but not the
protocol library's session, so only half of it can be driven from here. Left
with the analysis rather than fixed on a test that would not have caught it.
