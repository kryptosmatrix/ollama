Phase 3d — the OAuth handler
Falsification record

Method: each protection was broken in mcp/oauthhandler.go, the test that exists
to catch it was observed to fail, and the file was restored byte-identical.
Restored hash is printed after every attempt and equals the hash taken before
the first sabotage: 09a2ac4060d1a1115670627b59e0e3173f082fe3ef4e063264cf2ed0f5de8c05

Ten protections, all falsified on the first attempt.

The one that matters most is F1. An MCP server connects at start-up, on a
configuration change and on every reconnect, and none of those may summon a
browser window the user did not ask for. A server that answers 401 would
otherwise be able to open a sign-in page on a machine nobody is sitting at.
F1 wires the real loopback fetcher into the ordinary path — which is exactly
the mistake a later refactor would make, since it is one branch shorter — and
the test fails.

Two tests were rewritten before this pass because they did not discriminate,
and are recorded here rather than quietly fixed:

  - TestAnOrdinaryConnectionCannotOpenABrowser called refuseSignIn directly.
    That proves a refusal exists, not that an ordinary connection is wired to
    one; F1 would have passed. It now goes through session.fetch, which is what
    the handler itself calls.
  - TestAnOrdinaryConnectionOpensNoListener probed 127.0.0.1 port 80. A real
    listener binds an ephemeral port, so nothing would have answered there
    either and F2 would have passed. It now asserts the declared redirect is
    the unusable placeholder, and probes that address.

Both changes required the session to carry its redirectURL and fetch, which is
why those fields exist: the properties were not observable without them.

Note on F7. Removing the nil-store guard makes newOAuthSession panic on
store.Load rather than return an error, so the test fails on a segfault. The
protection is real — a handler with nowhere to keep tokens would sign the user
in and lose it — but what the guard buys is a message instead of a crash. The
falsifier discriminates; it just does so noisily.

Not falsified, and stated rather than implied: RequestRefreshToken is set true,
and nothing here proves it. Without a refresh token the user is sent back to
the browser each time the access token expires, but the field is consumed
inside the protocol library and observing it needs a fake authorization server,
which this package does not yet have. It is owed with the sign-in flow tests.
