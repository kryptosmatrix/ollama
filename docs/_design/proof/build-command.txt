Ollama BUILD.command — packaging this branch into an app and a disk image

Run 2026-08-09 from a cold cache. Exit 0, eleven minutes eight seconds.

WHAT IT WRAPS, AND THE TWO THINGS IT ADDS

scripts/build_darwin.sh already builds everything. This calls it rather than
reimplementing it, so the repository has one build and not two that drift.

  1. It creates the .dmg unconditionally. In build_darwin.sh the disk image is
     produced inside the code-signing branch, so a build without Apple
     credentials yields Ollama.app and a zip and no image at all — which is
     exactly what was asked for here.

  2. It points GOCACHE at a temporary directory. build_darwin.sh runs
     `go clean -cache`, which otherwise wipes the cache of whoever ran it and
     makes the next ordinary `go test` in this repo rebuild the world.

WHY IT IS A FULL UNIVERSAL BUILD

build_darwin.sh accepts `-a arm64`, but _prepare_darwin_runtime lipos
dist/darwin-amd64 and dist/darwin-arm64 together unconditionally when it
assembles the runtime. A single-architecture build therefore fails at that step.
Making it optional means changing their script, which is a larger decision than
a packaging convenience should take, so the wrapper builds both and says so
before it starts.

WHAT THIS BUILD IS NOT

Unsigned and un-notarised. Gatekeeper refuses it on first open; the script says
how to get past that. It is also unsuitable for testing the in-app updater,
which is what build_darwin.sh itself warns about when signing is skipped.

The version stamped into this particular run ends in "-dirty" because the
script and the .gitignore entry were still uncommitted when it ran. A build made
after this commit stamps a clean version.

THE FAILURE — ours, fixed
-------------------------

    /var/.../createdmg.tmp...:396:408: execution error: Finder got an error:
    AppleEvent timed out. (-1712)
    Failed running AppleScript
    BUILD FAILED: create-dmg.sh failed.

create-dmg lays out the disk-image window by driving Finder over Apple Events.
Its template ends in an unbounded wait:

    scripts/support/template.applescript:64-71
        set waitTime to 0
        set ejectMe to false
        repeat while ejectMe is false
            delay 1
            ...
            if (do shell script "[ -f " & dsStore & " ]; echo $?") = "0" then set ejectMe to true
        end repeat

There is no timeout and no give-up path: the loop spins until Finder writes a
.DS_Store to the mounted volume. That needs a GUI session that is awake,
unlocked and answering Apple Events. An eleven-minute unattended build does not
reliably have one — the screen locks part-way through — and the enclosing
Apple Event then dies with -1712, taking a build that had otherwise fully
succeeded with it. create-dmg.sh:501-508 turns that into exit 64, and the
wrapper turned exit 64 into a failed build.

The app had been built. The only thing that failed was the window cosmetics.

Fix: the cosmetics are no longer allowed to decide whether the build succeeds.
The styled image is attempted under a deadline; if the screen is locked, or the
Finder step fails or overruns, a plain image is built instead with create-dmg's
own --skip-jenkins. The Applications symlink is made during the copy step
(create-dmg.sh:453), not by the AppleScript, so a plain image is still a usable
one — it just has no background picture and unpositioned icons.

WHAT THE FIRST FIX GOT WRONG
----------------------------

The first version of the fallback timed the Finder step out and killed it —
but killed only the shell leading it. create-dmg's `hdiutil create` is a child,
and it kept running: it was still copying the app into a volume that the
cleanup had just detached, and it printed

    could not access /Volumes/Ollama .../Squirrel - Input/output error
    hdiutil: create failed - Input/output error

into the middle of the fallback. The fallback happened to succeed anyway,
which is the dangerous part — a run that passes while an orphaned process
races it teaches you nothing.

Caught by running the fallback for real rather than reasoning about it.
Fixed by giving the attempt its own process group (`set -m`) and signalling the
group, with a guard that refuses to signal the group if it turns out to be this
script's own — and by detaching in a loop until none of our images remain
instead of once.

The kill now has a test with teeth: a stand-in that spawns a grandchild, killed
through the same code path, asserting the grandchild is gone. Sabotaging
kill_job back to the single-process form makes it fail with
"grandchild 33266 survived the kill".

THE KILL HAS ITS OWN TEST
-------------------------

kill_job and run_with_deadline were extracted verbatim from the script into a
harness whose stand-in for create-dmg spawns a grandchild, exactly the shape
that survived the old kill:

    deadline status = 124 (want 124)
    ok    the whole job died, not just its leader

Sabotaged back to signalling the leader alone, the same harness says:

    FAIL  grandchild 33266 survived the kill

which is what a test that only asserted "the deadline fired" would have missed.
