Phase 3d — a complete sign-in against a real hosted service, and the defect it found

WHAT HAPPENED

The first run against Sentry's hosted MCP server failed, after the operator had
been to the browser and come back:

    SignIn: connect: calling "initialize": sending "initialize": rejected by
    transport: authorization server does not advertise RFC 9207 iss parameter
    support but iss was received in the authorization response

Sentry's authorization server returns the RFC 9207 "iss" parameter in its
authorization response. Its metadata does not advertise
authorization_response_iss_parameter_supported. The protocol library treats
that combination as fatal, so Ollama could not sign in to Sentry at all.

Checked against all three services this branch has verified — none of them
advertises the parameter:

    mcp.sentry.dev    authorization_response_iss_parameter_supported: absent
    mcp.linear.app    authorization_response_iss_parameter_supported: absent
    mcp.notion.com    authorization_response_iss_parameter_supported: absent

WHOSE DEFECT

The protocol library's, at auth/authorization_code.go validateIssuerResponse.
RFC 9207 asks a client not to *rely* on an unadvertised issuer; it does not ask
it to reject one. A server that never committed to sending an issuer offers no
mix-up defence whether it sends one or not, so the safe reading is to ignore
it — rejecting turns a harmless extra parameter into a sign-in nobody can
complete. This is worth reporting upstream to modelcontextprotocol/go-sdk.

WHAT OLLAMA DOES ABOUT IT

Not a blanket drop, which would have traded one broken server for a silently
weakened check on every compliant one: dropping the issuer everywhere makes a
server that *does* advertise it fail with the opposite complaint, and that
check is where the mix-up defence actually lives.

Instead the metadata is looked up once per sign-in, and the callback forwards
the issuer only when the authorization server said it would send one. A lookup
that fails answers "advertised", so not knowing keeps the stricter behaviour
rather than guessing the laxer one.

WIRING IT EXPOSED A SECOND THING. The fix went into oauthHandlerFor, and the
regression test still failed. That function had become dead when the transport
was restructured to stop registering clients: production called newOAuthSession
directly, and oauthHandlerFor survived only because its own test kept passing.
It has been deleted and the property it guarded — a stdio server gets no
authorization machinery — asserted against the transport that is actually
built.

Every stage against a real authorization server: discovery, dynamic client
registration, PKCE, a browser a person finished by hand, the token exchange,
nine real tools converted, a second manager over the same store reconnecting
with no browser at all, and a sign-out that Sentry accepted — the revocation
endpoint took the client identifier recorded at registration and the refresh
token, which is the whole reason SignInRecord carries a ClientID.

The credential is gone from both ends: revoked at Sentry, deleted from the
temporary store the run used. Nothing was written to the operator's keychain.

The regression is now deterministic and does not depend on Sentry: the fake
authorization server in mcp/oauthflow_test.go can send an issuer it never
advertised, which is exactly what Sentry does.
