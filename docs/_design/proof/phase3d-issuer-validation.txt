Phase 3d — RFC 9207 issuer handling, corrected

An earlier version of this fix was wrong, and reading the RFC properly rather
than paraphrasing it is what caught it.

The first fix dropped the "iss" parameter whenever the authorization server had
not advertised authorization_response_iss_parameter_supported, on the reasoning
that a server which never promised an issuer offers no mix-up defence anyway.
That reasoning does not survive RFC 9207 §2.4, which says clients that support
the specification must extract the iss parameter from responses they receive
"if the parameter is present", compare it with the issuer of the server the
request was sent to, and reject the response on a mismatch. The obligation is
conditioned on the parameter being present, not on it having been advertised.

So the earlier fix accepted a callback naming a different authorization server
without a murmur — precisely the attack the parameter exists to catch, and on
the one real service this branch has signed in to, because Sentry does not
advertise the parameter.

What it does now: the issuer identifier is learned from the metadata at the
same lookup, and a present iss is compared against it whatever the server
advertised. A mismatch ends the sign-in with a message naming both. Only after
that check does the advertised flag decide whether the value is passed on to
the protocol library, which refuses a sign-in outright when it sees an
unadvertised one.

The discriminating evidence is in I5 below. Under that sabotage the "advertised"
case still passes, because the library catches it — and the "not advertised"
case fails, which is the half only this code can catch.
