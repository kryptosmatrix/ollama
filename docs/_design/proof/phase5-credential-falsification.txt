Phase 5 repairs — the credential pair

One defect with two outlets, fixed together because a user who scrubs one file
has no reason to look in the other.

WHAT WAS WRONG

validateURL checked the scheme and the host and never looked at the userinfo, so
https://alice:s3cr3t@api.example.com/mcp was accepted and Save wrote it to
mcp.json verbatim. And Approve stored spec.Summary() so a user could later read
what they had agreed to — Summary renders the URL as-is for an http server and
the command joined with its arguments for a stdio one — so the same credential,
or one passed as --api-key=... on a command line, landed in mcp-approvals.json
as well. The fingerprint beside it is a SHA-256 and gives nothing away; the
summary undid that.

THE TRADE-OFF, MADE EXPLICIT

The obvious fix is to redact Summary. That would be wrong. The approval prompt
is where a user reads exactly what will run before agreeing to it, and the app's
shown-value check compares against that same string; redacting it would hollow
out the gate this package is built around and would let a stale page approve
something the user could not fully see.

So the split is: Summary stays verbatim for the decision, and a separate
redactedSummary is what gets written down afterwards. The ledger is a record,
not a decision, and matching is done by the fingerprint. C5 below is the
falsifier for that direction specifically — it redacts the prompt and the test
fails, which is what keeps someone from "simplifying" the two functions into
one.

Redaction is deliberately eager. A value withheld that was not a secret costs a
little detail in a record; a value kept that was one costs the user their
credential.

WHAT WAS DELIBERATELY NOT DONE, and it is a judgement worth disagreeing with

The review also raised credentials in the query string (…?api_key=…). That is
not fixed, and not because it is unreal. Refusing it needs a rule that matches
parameter names, and there is no ${env:NAME} mechanism for URLs the way there is
for headers — so a user whose server genuinely needs a query parameter that
trips the rule would have no way to proceed at all. A name-matching rule would
also refuse legitimate URLs: secretishEnvKey matches "token" anywhere, so a
parameter like pagination_token would be rejected.

Userinfo is different in kind: it is a credential or it is nothing, so refusing
it strands nobody. That asymmetry is the whole reason one is fixed and the other
is recorded. Ruling on the query-string case belongs to the operator, and the
options are narrow (a tighter name list, a warning channel Problems() does not
currently have, or leaving it).

FALSIFICATION

Five protections, each broken in production code, the test observed to fail, the
file restored byte-identical.
