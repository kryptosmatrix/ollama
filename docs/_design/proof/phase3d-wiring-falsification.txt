Phase 3d — the wiring and the connect surfaces
Falsification record

Method: each protection was broken in production code, the test that exists to
catch it was observed to fail, and the file was restored byte-identical.

Ten protections, all falsified. Four of them appear twice, and the reason is
recorded rather than tidied away.

  W4, W5 and W6 act on app/ui/mcp.go. The first harness backed every file up to
  /tmp/<basename>, and this repository has two files called mcp.go —
  app/ui/mcp.go and cmd/mcp.go. The second backup overwrote the first, so
  restoring app/ui/mcp.go after W4 wrote cmd/mcp.go's contents into it: the
  whole app-side MCP surface was replaced by the CLI's. W5 and W6 then could
  not find their sabotage targets, which is how it was noticed — a falsifier
  that cannot apply reads exactly like one that passed, and both were reported
  as SABOTAGE DID NOT APPLY rather than skipped.

  The file was recovered from HEAD plus the additions re-applied, checked by
  `go build`, the app suite, and a diff showing 145 added lines against one
  changed. W4, W5 and W6 were then re-run against a backup with a unique name.
  Their re-runs are at the end of this file and are the authoritative ones; the
  first W4 result stands as a falsification (the sabotage did apply and the
  test did fail) but its restored-hash line is not to be trusted.

  The lesson is worth keeping: a harness that names its backups by basename is
  a data-loss bug waiting for a repository with two files of the same name, and
  this one has several.

The protections that carry the most weight:

  W1  The http transport built without the OAuth handler. This is the wiring
      itself, and its failure is silent: a server needing authorization answers
      401 and simply never connects, which looks like the server being down.
      Nothing else in the package would notice, which is why this test was
      written before the falsification pass rather than after.
  W2  and W3  A closed server never giving back what its transport held. A
      redirect listener outliving its sign-in leaves a loopback port bound for
      the life of the process.
  W4  The sign-in route bypassing the approval gate. A sign-in contacts the
      server, so it goes through the gate that says a server may be contacted.
  W5  and W7  The user never being told where their credential will be kept.
      The file store is weaker than the operating system's keychain, and that
      has to be said before a token exists, not after.
  W6  A failed revocation reported as a clean sign-out. The token was deleted
      either way; what did not happen is the revocation, and the user has to
      know which of the two it was to know whether they still have something to
      withdraw.
  W8  The commands not registered on the group. A command that works but is not
      reachable is not a feature.
